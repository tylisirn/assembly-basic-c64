# Assembly BASIC implementation summary

The original design document was committed first as `9480026`. The project now contains a working native-code development cartridge, a reproducible build, source-file tools, automated tests, examples and synchronized design documentation. The full version-one release contract is **not yet complete**; the outstanding requirements are listed in [docs/IMPLEMENTATION_STATUS.md](docs/IMPLEMENTATION_STATUS.md) and design Appendix B.

## Firmware

The cartridge initializes the C64 explicitly and supplies its own editor, tokenizer, two-pass compiler and runtime. The compiler generates 6502 instructions on the target machine. It retains binary source tokens next to each exact-sized native body; seven-byte stable anchors and each body's final successor JMP support ordered editing, forward branches and LIST without relocation tables.

RUN hides cartridge and KERNAL ROM with the `$35` execution map. Fixed-address helpers execute in upper RAM. Common-RAM gateways provide KERNAL calls, IRQ/NMI handling, SYS/USR return recovery and source transport. The raw runtime is copied from Magic Desk bank 2 at startup, RUN and CONT. Bank 1 supplies the resident compiler image at startup. Source and code can occupy cartridge and KERNAL shadow RAM.

Implemented language facilities include wrapping integer arithmetic, arithmetic shifts and word RND, signed formatting and comparisons, hexadecimal immediates, full identifier identity, strings, multidimensional numeric/string arrays, compiled DEF FN, IF/THEN/ELSE and ON, GOSUB, dynamic FOR/NEXT, DATA/READ/RESTORE, STOP/CONT, memory/device operations and clock access. Payloads allocate from the high end of free spans to preserve common RAM for stable anchors and bindings. A coalescing allocator and registered-root nonmoving string collector preserve stationary code and continuation PCs.

SAVE emits the design's source-only version-one container with dense referenced-name IDs and CRC. LOAD builds a second source graph, validates it and publishes it after completion; failures retain the old source. The host tools provide stricter format validation, canonical source exchange and a console executing the assembled cartridge through py65.

## Revision 0.6 — 64 KiB Magic Desk

The cartridge now uses classic Magic Desk CRT type 19 with eight 8 KiB banks at `$8000–$9FFF`. Bank 0 contains commands, editing, tokenization, LIST, source transport and the common-RAM gateway load image. Bank 1 contains the raw resident compiler and bank 2 the raw execution runtime. Banks 3–7 have recovery headers and erased space reserved for the improved editor/PRG converter, 16.8 fixed-point/PRINT extensions, VIC/SID/sprite commands, resources and expansion. The [bank architecture](docs/MAGIC_DESK_BANKS.md) defines the layout and future integration requirements.

The linker assigns fixed RAM run addresses and banked ROM load addresses in one build. Startup copies the compiler and runtime through a common-RAM banking routine; RUN and CONT refresh the runtime. The compressed-image/decompression build path is replaced with direct bank copies. Bank changes occur in common RAM, preserve the bank shadow, full port and interrupt flags during copies, and preserve bank state across KERNAL/IRQ service frames. NMI remains in RAM. SYS/USR recover bank 0 even when user code changes the I/O map; every bank supplies cold/warm recovery vectors.

The current language features remain intact, including the Void Runner fixes. Future editor, PRG, numeric, PRINT and hardware commands are not implemented by this conversion. Runtime ABI changes to 4 because gateway addresses/load architecture changed; `.AB` containers remain source version 1. The compiler still reserves 6 KiB of RAM and the raw user arena remains 42 KiB. Hard-reset and reload/reenter source after attaching this cartridge; previous snapshots contain the old runtime and native references. `tools/package.py` publishes artifacts only when build, tests and synchronized design identify the same ROM.

## Revision 0.5

The editor outputs the carriage return received from CHRIN through CHROUT before processing each submitted command, numbered line, deletion or blank line, so subsequent output and input start on the next screen line. Numbered entry and deletion resume input without READY. Recoverable lexical/compilation failures report a diagnostic immediately and retain the new source and a deferred error stub, including malformed DATA fields. LIST begins on a new line and accepts exact numbers, inclusive ranges and open endpoints.

ELSE binds to the nearest unmatched IF on the same physical line; arms can contain colon-separated statements or literal line targets. RND returns a full 16-bit word from a full-period LCG. Its first positive call seeds from the KERNAL clock; positive calls advance, zero repeats, and negative arguments reseed reproducibly.

The compiler supports arithmetic `<<` and `>>`, with shifts below addition and above comparisons. Counts are checked bytes, and counts ≥16 produce zero/sign fill. Literal power-of-two multiplication in either operand becomes a left shift. Power-of-two literal division becomes a biased arithmetic right shift, preserving signed truncation toward zero; redundant parentheses and unary plus on literals are accepted. The `$8000` divisor is signed -32768 and additionally negates the shifted quotient.

Direct CLEAN rebuilds dense anchor slabs and a dense referenced-name dictionary from a temporary source snapshot, remaps token IDs and recompiles all branches, cells, array/function records and native references. It keeps referenced missing targets, discards historical unreferenced slots/names, clears values and invalidates CONT. Allocation failures during snapshot or staged compilation retain the old source and release temporary allocations. This requires temporary headroom; it is not general sliding compaction of every allocation.

For the earlier standard 16 KiB cartridge, the compiler was linked for a 6 KiB resident reservation at `$1400–$2BFF` and stored compressed alongside the runtime. Revision 0.5 decompressed both fixed-address images. Its raw user arena was 42 KiB and runtime ABI was 3; source containers remain version 1 with additive shift/ELSE/CLEAN token codes.

## Void Runner runtime correction

The reported VICE JAM after gameplay initialization came from a memory ownership conflict. Compiled BASIC lines 400/410 occupied $C200 while Void Runner wrote its star-field coordinates there. A trace of the original pasted source reached overwritten code and a JAM opcode at $C210, consistent with the user's $C207 report and different edit/allocation histories. Sprite writes at $3C00 also needed explicit protection from future allocations.

The new `RESERVE address,bytes` declaration (token $6A) removes whole pages from a free arena span before compilation allocates source/code. Arguments are unsigned literals aligned to 256 bytes; the nonempty range must fit one arena span. Eight regions can be recorded outside user RAM. Free-list splitting preserves valid headers, and collection skips reserved pages without interpreting graphics/native bytes as allocation metadata. Exact repeats are harmless; live/overlapping allocations are rejected. Declarations act during compilation outside IF, including LOAD and CLEAN. They persist through RUN, CLR and edits; NEW releases them. Removing a declaration or a failed import may leave a reservation until NEW. POKE/SYS remain caller-managed memory operations.

Void Runner's first line now reserves $3C00–$3DFF for sprites and $C000–$C2FF for native code/workspace. Its stock BASIC POKE 55/56 memory-top idiom was removed because those locations belong to this language's zero-page state. Existing copies must be cleared with NEW and reentered with the updated first line before compilation. The source loader also now accepts zero-length STRING/DATA_TEXT payloads instead of mistakenly checking the token code as their length.

In revision 0.5, the LZSS packer minimized encoded size including eight-item flag overhead without changing its format. Program reset/clear helpers moved into the compressed compiler image, with a larger prefix occupying the first cartridge bank. Those changes fit the reservations into the former 16 KiB cartridge and fixed RAM budgets.

## Void Runner collection pause correction

The later VICE 2.4 snapshots show valid, progressing garbage collection during the score-string update on line 1930. Repeated whole-free-list and root scans for each of 1,636 physical blocks made the machine appear frozen, with the SID retaining its last waveform. This differs from the earlier memory-overwrite JAM.

The collector now sweeps free blocks with monotonic cursors and marks roots once per 2 KiB window using a 256-byte bitmap over inactive lexer scratch. It retains stationary payloads, full 16-bit sizes and reserved regions. On the captured heap, complete revised collection takes 393,741 instructions / 1,269,365 simulated CPU cycles, compared with 44,268,554 instructions / 137,980,792 cycles just to finish the old collection from the first halt. The final free list and all live allocations match exactly. Collection still causes a finite pause; these are instruction-level measurements without VIC/IRQ timing. [The investigation report](docs/VOIDRUNNER_FREEZE.md) records evidence, tests and retest instructions.

Allocator wrappers and error output moved into the resident compiler reservation. The earlier 16 KiB build split compressed images across its ROM windows; revision 0.6 replaces that arrangement with raw bank images while retaining the collector improvements.

## Measured build and verification

The exact linked section sizes, ROM checksum and memory boundaries are recorded in [dist/size-report.json](dist/size-report.json). The 65,536-byte cartridge uses runtime ABI 4 at `$E400`, with a 7,162-byte runtime reservation, a 6,144-byte compiler reservation, 3,072-byte common workspace and 43,008-byte raw user arena. The runtime occupies 6,774 bytes, compiler 6,116 bytes and gateway 538 bytes. ROM contents use 19,947 bytes, leaving 45,589 bytes distributed among eight banks. Compiler RAM headroom is still 28 bytes; using spare ROM for future executable helpers requires a deliberate bank-call/RAM-layout design.

Run `python3 tools/build.py` and `python3 tools/test.py` after the optional checksum-pinned local bootstrap. All 78 regression tests pass. The suite checks the eight-bank Magic Desk CRT packet layout and executes the native machine code to check word semantics, all word encodings, source round trips and corruption, randomized edits, array/function/string behavior, exact anchor/trailer layout, execution beneath ROM, map recovery, IRQ/NMI frames, clock setting, frozen continuations, source-load rollback and runtime refresh, resident compiler protection, screen Enter cursor advancement, ranged LIST, entry diagnostics, nested ELSE, deterministic RND, shift precedence/counts, signed power-of-two lowering, CLEAN remapping/rollback at seven allocation points, reservation boundaries/idempotence/conflicts/table limits, preservation of arbitrary user bytes through allocation/collection, empty source strings, and both pasted and .AB-loaded Void Runner reaching twelve native gameplay frames with every compiled body unchanged. Additional collector tests replay the captured heap, check bitmap boundaries and full-word sizes, and force automatic collection during repeated score formatting. New banking tests check latch/PLA visibility, exact raw image copies, bank/port/flag restoration, IRQ and NMI during banked work, KERNAL bank recovery, SYS/USR changing bank and I/O visibility, and auxiliary-bank warm recovery. A static runtime check rejects undocumented instructions and ordinary helper calls outside the copied runtime or declared low-RAM gateways.

[docs/measurements.json](docs/measurements.json) records reproducible instruction counts and line-layout measurements from the deterministic harness. The cold-NEW capacity scenario stores 690 lines of `<number> A=A+1`; line 691 fails safely with 46 free physical bytes remaining. Capacity depends on source, names, allocations and fragmentation. Cold start now takes 176,411 harness instructions versus 493,293 for the preceding compressed build. These are development measurements, not C64 timing or hardware speedup claims. The build was reproduced with checksum-pinned cc65 and py65 dependencies; the example programs were encoded, decoded, verified and executed through the native cartridge.

## Design synchronization and limits

The design is revision 0.6. Its Magic Desk bank plan, memory map, fixed runtime addresses, raw load images, actual interning and collection strategies, workspace and measured budgets match the implementation. Appendix B explicitly identifies incomplete release requirements. The original version-one goals remain visible instead of being silently removed.

The important unfinished areas are general arena compaction; full INPUT/GET behavior; software-stack function activations; every target-side DATA_SPELLING validation rule; canonical target VERIFY for differently numbered dictionaries; graph/interrupt/failure hardening; and cycle-accurate, genuine-ROM, PAL/NTSC and real-device acceptance tests. The checked-in cartridge should be treated as a development artifact until these are completed.

The new CRT was checked against VICE 3.7.1 `cartconv -t md`: all header and packet bytes match except the cartridge name, and conversion back to binary reproduces the ROM exactly. This verifies cartridge packaging; genuine-ROM, cycle-accurate and physical-machine execution still require acceptance testing. Load the `.crt` through VICE's CRT attachment; a raw `.bin` now requires Magic Desk attachment rather than generic 16KB.
