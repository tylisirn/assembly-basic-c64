Assembly BASIC for the Commodore 64
Implementation design for an integer and string BASIC ROM cartridge
Implementation status: working development cartridge; the full version-one release is not complete. See Appendix B for measured implementation facts, explicit differences and pending acceptance work.
Design specification  |  Version 0.16  |  24 October 2026
Implement Assembly BASIC as a 64 KiB classic Magic Desk autostart cartridge containing the command/editor firmware, tokenizer, compiler and an execution runtime load image. Copy compiler/runtime helpers to fixed RAM and execute native programs with cartridge, BASIC and KERNAL ROM hidden. Retain custom tokens beside native code and link each body through its final successor JMP. LIST expands source tokens into canonical PETSCII.
Use a seven-byte stable anchor per line and a single allocation containing its tokens and native body. Bind full identifiers to an interned name dictionary. Keywords, operators and the first 128 name references each occupy one byte; valid integer immediates are binary values. Runtime calls use fixed RAM helpers or common-RAM service entry stubs. Cold DATA/READ/RESTORE, DEF FN activation and device/input helpers execute from bank-2 ROM through bank_call; hot arithmetic, arrays, strings, function calls and collection remain in RAM.
Version 0.3 replaces the earlier ROM-resident execution model, 32-byte nodes and stock BASIC token storage. It adds RAM beneath both cartridge ROM and KERNAL to the allocation map, removes persistent statement and relocation tables, and adopts the custom source format specified in Appendix A. Source and file tokens have no binary compatibility requirement with stock BASIC. Familiar BASIC syntax, integer/string behavior and device interaction remain the compatibility goals.
Full identifiers, $-prefixed hexadecimal constants and modulo-65536 arithmetic remain part of the language. Decimal 53248 and hexadecimal $D000 both store the word $D000, displayed as -12288. V=53248:POKE V+33,1 and V=$D000:POKE V+33,1 both write 1 to I/O address $D021 under the execution map. The fixed runtime and cartridge size budgets are engineering targets that require implementation measurements.
1 Requirements and architectural decisions
Requirement	Implementation decision
Tokenize on entry	Use custom one-byte token codes, interned name references and binary integer immediates; Appendix A is normative.
Generate runnable assembly	Emit documented NMOS 6502 machine code immediately after tokenization; share hot semantics through copied RAM helpers and cold services through common-RAM banked ROM calls.
Expand program RAM	Bank ROM out for execution with port bits 2..0 equal to 101; keep I/O visible and reserve an execution image at the top of RAM.
Link lines in numeric order	Use the final JMP operand as both the execution successor and the sorted linked-list next pointer.
Compact line metadata	Seven-byte stable entry plus one token-length byte and a two-byte shared allocation header; derive body length and trailer location.
Integer and string variables	16-bit words with signed unsuffixed and unsigned % interpretation and wrapping arithmetic, and strings up to 255 bytes; every identifier character is significant.
LIST canonical source	Expand custom codes and dictionary names, format binary values, and preserve raw string/comment bytes.
Replace stock BASIC	64 KiB classic Magic Desk cartridge, eight 8 KiB ROML banks selected through $DE00; /EXROM low and /GAME high. No cartridge RAM is required.

The cartridge stores both the command firmware and the load image of the RAM runtime. Compilation, listing, editing, execution and file conversion occur on the C64. No external compiler is needed. The CPU banking port can hide a normal cartridge without changing its /GAME or /EXROM wiring. RAM at $D000-$DFFF is deliberately excluded from user allocation because the execution map keeps hardware I/O visible. [8]
Native code does not call the stock BASIC evaluator. Assembly BASIC supplies its own integer math, strings, arrays, control flow, numeric conversion and BASIC-level I/O adapters. KERNAL remains available through a common-RAM bank gateway, with ROM mapped only for the duration of each service or command operation. Ordinary arithmetic, branches and line chaining stay in RAM.
2 Compatibility contract
Source syntax and identifiers
Accept decimal line numbers 0 through 63999, colon-separated statements, optional LET, PRINT abbreviated as ?, standalone BASIC V2 keyword abbreviations, quoted PETSCII strings, REM, DATA, decimal and $-prefixed hexadecimal immediates, and the usual statement and expression punctuation. Line numbers remain unsigned decimal compiler metadata, not wrapped integer expressions; hexadecimal line labels and hexadecimal GOTO targets are not added.
Identifiers consist of a letter followed by letters or digits and an optional final % or $ suffix. Every character is significant. Canonicalize letters to uppercase for comparison, so Score and SCORE are the same variable while SCORE and SCORETOTAL are distinct. The name dictionary stores a one-byte length and up to 255 name bytes, including the suffix; there is no two-character aliasing or shorter name limit. Interactive entry remains bounded by the screen editor’s 80-character line limit. Imported compact source can refer to a longer dictionary name without repeating its spelling in each line. Numeric names without a suffix hold signed 16-bit words; names ending in % hold unsigned 16-bit words (0..65535). They remain distinct namespaces. Arrays and function parameters/results follow their declared suffix. Assignment and parameter/result conversion copy all 16 bits without overflow or range checks. Names ending in $ are strings; scalars and arrays are distinct entries. Unassigned values are zero or an empty string. This intentionally replaces stock BASIC V2’s two-character identity rule. [4]
The lexer consumes a complete identifier before testing the reserved-word table. Only an exact reserved name becomes a keyword token; embedded keywords are ordinary name characters, allowing TOTAL, COSMIC and SCORE. Exact keywords and special variables such as PRINT, LEFT$, TI and TI$ remain reserved. Keyword abbreviations are accepted only as standalone keyword lexemes. Require a separator between a keyword and an identifier or decimal target: PRINT A and GOTO 30 are valid, whereas PRINTA and GOTO30 denote identifiers. Likewise use DEF FN DOUBLED(X)=X*2 and FN DOUBLED(3) for a full function name. PRINT#, INPUT#, GET#, TAB( and SPC( retain their punctuation forms.
Area	Version 1 contract
Preserved	Numbered editing, familiar BASIC source syntax, strings, arrays, line control flow, PETSCII screen interaction and KERNAL device I/O.
Changed	Full-length name identity and keyword boundaries; decimal/hex word literals; signed unsuffixed and unsigned % variables, mixed signed arithmetic, wrapping and type-directed formatting.
Unsupported numeric features	Fractional constants, E-format constants, π, SIN, COS, TAN, ATN, EXP, LOG and SQR have no floating-point fallback. RND is implemented as a random 16-bit integer function in revision 0.5.
Internal binary compatibility	Stock tokens, variable tables, program-memory addresses, BASIC ROM entry points and extensions are incompatible; Appendix A defines the replacement format.
External source files	Versioned Assembly BASIC source container with a name dictionary and binary token records; canonical text is the exchange representation.
Machine-code interaction	SYS/USR enter the RAM map; KERNAL services require the documented bank gateway. Stock BASIC internals and unguarded ROM calls are outside the contract.

Word literals and integer semantics
Each numeric value stores a 16-bit word plus an expression interpretation. Unsuffixed names are signed; % names and FRE results are unsigned. Nonnegative decimal/hex constants, including zero, are unsigned; negative literals are signed, including -32768. Literal magnitudes above 65535 are rejected. Signed interpretation of word u is u below 32768, otherwise u-65536; unsigned interpretation is u. Evaluation follows the expression tree independently of the destination. Assignment and parameter/result conversion preserve all 16 bits without range checks. PRINT 20000+20000 produces 40000, whereas assigning it to A produces -25536 and to A% produces 40000. The integer contract is detailed in docs/integer_arithmetic_design.md; A# fixed point is a future extension.
Hexadecimal immediates use $ followed by one through four hexadecimal digits, accepting A-F in either case. $D000, $d000 and decimal 53248 produce the identical word. Hex constants are allowed wherever a numeric expression is allowed, including POKE values, subscripts, DATA numeric fields and function arguments. A bare $ or an attached nonhex character raises ?SYNTAX ERROR; more than four digits raises ?ILLEGAL QUANTITY. Require a delimiter after the digits. A trailing $ on an identifier still marks a string variable, so VALUE$=$D000 is a type mismatch rather than a different numeric declaration.
Addition, subtraction, multiplication, unary negation and nonnegative-integer exponentiation return the low 16 bits of the mathematical result. This modulo-65536 rule is uniform for variables and constants: 32767+1 becomes -32768, 65535+1 becomes 0, and $FFFF*2 becomes -2. Arithmetic wrap is normal behavior and does not raise ?OVERFLOW. Constant folding uses the same reductions at each operation. The low word of a signed and an unsigned product is identical, so multiplication shares a bit-level helper; the expression tag determines result interpretation.
Binary operations use unsigned interpretation only when both operands are unsigned; mixed operations reinterpret both words as signed. A naked literal adopts the directly combined typed expression interpretation when representable. A computed constant subexpression retains its type; context never changes earlier operations. For U%=40000:B=2, U%/2 is unsigned 20000, U%/B is signed -12768, and with B=-2 it is 12768. Constant-only 4-5 wraps unsigned to 65535; (4-5)/2 is 32767. Addition, subtraction and multiplication retain the low 16 bits at every operation. Signed division truncates toward zero; unsigned division returns the floor quotient. Zero divisors raise ?DIVISION BY ZERO; quotients wrap. Comparisons return signed -1/0. Typed unary minus and NOT preserve type; negative literals are signed. INT and ABS preserve type; signed ABS(-32768) remains -32768. Power requires a nonnegative exponent under the selected interpretation, and x^0 is 1. Explicit arithmetic >> retains sign fill for both word types.
PRINT and STR$ select decimal formatting from the expression type: unsigned values print 0..65535, signed values print -32768..32767, using the existing Commodore positive-space/separator conventions. PRINT $D000 displays 53248; V=$D000:PRINT V displays -12288. INPUT and READ copy parsed word bits into the declared target type. VAL still returns a signed word using the shared decimal/hex decoder and longest-prefix policy; malformed hex, oversized magnitudes, fractional and scientific continuations remain rejected.
Preserve eager integer evaluation and BASIC precedence with shifts inserted below addition and above comparisons. Highest to lowest: power (left associative), unary +/- , multiplication/division, addition/subtraction, << and >> (left associative), comparisons, NOT, AND, OR. Relational results are -1 or 0. Shift counts are checked unsigned bytes 0..255. Left shifts wrap the word; arithmetic right shifts repeat its sign bit. Counts of 16 or more produce zero or sign fill. Numeric/string mixing requires explicit conversion; string comparisons use unsigned PETSCII order then length.
Unsigned addresses and special values
PEEK, POKE, WAIT and SYS evaluate their address expression with the ordinary word rules and reinterpret its final 16 bits as an unsigned address from $0000 through $FFFF. They must not reject a negative signed representation or sign-extend it into a larger address. No address-only literal exception is needed. The same rule works for direct constants, variables, array elements and computed expressions, including POKE 53248+33,1 and POKE $D000+$21,$01.
Expression or statement	Required result
V=53248 or V=$D000	V stores bytes $00,$D0; signed value -12288.
V+33	Word $D021; signed value -12255; address 53281.
V=53248:POKE V+33,1	Write byte $01 to CPU address $D021.
V=$D000:POKE V+$21,$01	Same address and byte as the decimal form.
V=$7FFF:V=V+1	V becomes $8000, displayed as -32768; valid as address $8000.
V=$FFFF:V=V+1	V becomes $0000; addition wraps at the word boundary.

Two unsigned operands select unsigned comparisons/division; mixed operations remain signed. FOR limits use the declared loop variable interpretation with signed STEP direction. Byte arguments to POKE, WAIT and CHR$ must be in 0..255 for either numeric type. Subscripts, DIM sizes and allocation counts retain semantic bounds and checked wider products; wrapped numeric arithmetic never permits pointer or allocator overflow. USR still uses its configured vector and word A/X convention.
Keep ST as the KERNAL status byte and TI$ as the full six-digit time string backed by the KERNAL clock. Numeric TI returns the low 16 bits of the jiffy clock interpreted as signed; it is explicitly not stock TI’s full-range value. Only TI$ is assignable for setting the clock. FRE() and compatible FRE(n) collect unreachable objects and coalesce free blocks, then return the total free physical user-arena bytes as an unsigned word. FRE(n) evaluates and ignores its numeric argument. The count includes free-block headers and does not promise a single contiguous allocation. Runtime FRE preserves variables, arrays, source/native code, reservations and CONT; it does not run the destructive stopped CLEAN rebuild. PRINT FRE() therefore displays a positive count even above 32767. The count excludes workspace, runtime, anchors already allocated and reserved graphics or machine-code regions. POS, TAB and SPC keep their screen-related roles with integer arguments.
3 Cartridge hardware and system entry
Magic Desk cartridge and CPU maps
Use a 64 KiB classic Magic Desk cartridge with eight banks at $8000-$9FFF, /EXROM low and /GAME high. $DE00 selects banks 0..7; its write-only latch is shadowed at $0BE3. The command map sets LORAM, HIRAM and CHAREN: bank 0, stock BASIC at $A000-$BFFF, I/O and KERNAL are visible. No stock BASIC routines are called. Preserve cassette control bits and configure direction bits 0..2 as outputs. See docs/MAGIC_DESK_BANKS.md and the VICE Magic Desk format specification.
Mode	Port bits 2..0	CPU mapping
Command and KERNAL service	111, typically $37	Selected Magic Desk bank at $8000-$9FFF; BASIC ROM at $A000-$BFFF; I/O at $D000-$DFFF; KERNAL at $E000-$FFFF.
Native execution	101, typically $35	RAM at $8000-$BFFF and $E000-$FFFF; I/O stays visible at $D000-$DFFF.
All RAM for diagnostics	100, typically $34	RAM also replaces I/O; this is not the supported language execution map.

With classic Magic Desk, $35 hides ROML, BASIC and KERNAL while retaining I/O; $34 hides I/O too. Writes beneath visible ROM reach underlying RAM. Keep the cartridge enabled and select RAM through $01 rather than writing $80 to $DE00, since some physical variants latch disable until reset. VIC visibility follows its separate map.

The KERNAL recognizes CBM80 at $8004 before initialization. Bank 0 has cold/warm entry vectors at $8000/$8002. Every auxiliary bank has the same signature and vectors to common-RAM recovery helpers installed at startup; these select bank 0 before returning to command ROM. The previous $A000 recovery words are removed because stock BASIC ROM occupies that window in the command map.
Cold start and copying the execution image
Disable IRQs, clear decimal mode and establish a bounded hardware stack. Set the port direction and command map, preserving cassette control bits. Perform the audited IOINIT, RAMTAS, RESTOR and CINT startup sequence. Allocate language state and install hooks only after RAMTAS has cleared its work areas. Use explicit language memory boundaries rather than accepting the cartridge-aware RAM test as the allocator limit. [3, 6]
Link the execution runtime for fixed run addresses $E400-$FFF9 and the resident compiler for $1400-$2BFF (runtime ABI 7). Store raw load images in Magic Desk banks 2 and 1 respectively. Copy the complete dependency closures through common RAM at cold start; refresh the runtime at RUN and CONT. The linker supplies separate load and run addresses, so internal instructions already name their RAM addresses. Copy service entry stubs to $0334-$03FF after KERNAL initialization. Bank-2 DATA/READ/RESTORE, DEF FN activation and device/input services execute directly from ROM through the generic common-RAM bank_call ABI. Shared hot helpers remain in the copied runtime. There is no decompression or arbitrary instruction relocation.
Copy the common-RAM gateway image into its reserved workspace, and write the six RAM hardware-vector bytes at $FFFA-$FFFF underneath KERNAL. The vector targets are common-RAM interrupt entries. Finish all copies and validate their build stamp/checksum before enabling IRQs. The top RAM reservation is permanent, including while the ROM is visible; allocation must never use it as temporary editing space.
Before RUN, verify the runtime image and refresh it from ROM when required. CONT uses the same fixed helper addresses and may refresh identical bytes, but an ABI/build change or structural program change invalidates continuation. A helper copy does not recompile already valid user bodies. Hardware RESET performs cold initialization and does not promise retention.
Common RAM gateways
Every map-changing instruction sequence executes from common RAM. bank_call uses four inline descriptor bytes after JSR: bank (0..7 or $FF to retain current), port low bits (5 or 7), then a little-endian target word. It reads the descriptor in the caller map, advances the return address past it and saves full $01, bank and caller P on a per-call hardware-stack frame. Setup and return mask IRQs; the callee receives A/X/Y and the caller interrupt mask with D clear. Return yields A/X/Y and callee N/Z/C/V, restores full $01, bank and caller I, and clears D. Active calls add five stack bytes beyond an ordinary JSR, plus temporary dispatch and helper locals. Targets/returns are stacked before IRQ enable; nested calls safely reuse setup scratch. ROM code enters common RAM before changing banks/maps. read_ram handles shadow source reads, and RAM_CALL descriptors reach hot helpers with the current bank and map 5. KERNAL, command-to-RAM, source-file and image-copy gateways share bank_call; copies retain their fully masked IRQ and saved-flags contract. SYS/USR retain their own return conventions.
KERNAL gateways use bank_call to save the complete $01, interrupt state and bank shadow on each call frame. Expose I/O before selecting bank 0, preserve service arguments/results and carry, and restore the bank before the original complete map. Image copies reuse the ABI with IRQs masked throughout the copy and restore original flags. Every bank-selection instruction and its return path executes in common RAM. NMI stays in common RAM and leaves the bank and dispatch scratch unchanged.
A pointer passed to ROM must identify memory visible to ROM. Stage filenames, input buffers and file-transfer chunks in common RAM. CHROUT/CHRIN and register-only clock/status calls do not need high-memory payload pointers. The ROM compiler copies each token stream into low scratch before parsing; common-RAM read/copy gates provide access to hidden names, allocation headers and code. It may emit bytes into RAM under ROM using verified write-through behavior. [8]
Interrupts and asynchronous breaks
Keep IRQs active during native execution. RAM hardware IRQ/BRK and NMI vectors point to distinct common-RAM entries. The native IRQ entry saves A/X/Y and map state, enters the KERNAL map, invokes the stock IRQ path with a synthesized interrupt frame that returns to a low-RAM completion entry, restores the execution map and registers, and RTIs through the original hardware frame. The synthetic status has BRK clear and IRQ masking set. Audit stack depth and stock handler behavior on each supported KERNAL. [6]
Leave the ordinary KERNAL IRQ RAM vector directed at the audited stock IRQ service, so an IRQ occurring during a mapped KERNAL call takes its normal ROM path. Do not redirect that vector back into the raw RAM wrapper and create recursive dispatch. Separate BRK handling from the IRQ service and transfer to a deferred error at a safe language boundary.
NMI cannot be masked by SEI. Both the raw RAM-vector entry and the KERNAL $0318 entry preserve their documented entry frames, acknowledge the relevant CIA2 source, set a pending-abort flag and RTI. They do not allocate, edit pointers or return to READY inside a bank transition. Source polls service the request only after the mapping and allocator state are coherent. Version 1 excludes KERNAL RS-232 device 2 and arbitrary external NMI hooks until an explicit dispatcher is implemented.
A fatal runtime error, normal termination or nonresumable abort passes through a common-RAM ENTER_READY entry. It restores the command map before jumping to the ROM prompt/error handler and resets temporary stacks and channels. STOP uses the separate continuation path. Warm recovery validates the program and reinstalls hooks. Verify the cartridge $8002 and $A002 fallback entry stack shapes against the supported KERNALs; their contracts differ from a raw RAM hardware interrupt. [6]

The implemented allocator has two spans: [$2C00,$D000) and [$E000,$E400). Their raw total is 42 KiB (43008 bytes), before anchors, names, source, generated code, arrays, strings and free-block overhead. The $1400-$2BFF range is permanently reserved for a 6 KiB compiler image copied from bank 1 at startup. The $E000-$E3FF shadow span supplies 1 KiB; $E400-$FFFF is permanently reserved for the runtime and six vector bytes. This is the lower-runtime-base adjustment permitted by the original design.
These are ABI 7 build limits. The 65536-byte cartridge has eight 8192-byte banks. Set initial limits of 32 expression nesting levels, 255 token bytes per stored line and eight array dimensions. GOSUB frames use three bytes and FOR frames nine bytes, so the 512-byte mixed stack has theoretical maxima of 170 GOSUB or 56 FOR frames before function activations and other overhead. There is no persistent statement-entry table or separate 63-statement limit; the token limit and bounded parser counters constrain statement count. All counters and allocations are checked before writes.
Audit zero-page ownership for every supported KERNAL operation. Save overlapping language temporaries or avoid the locations. Place indirect-JMP pointers away from a low byte of $FF to avoid the NMOS page-boundary bug. RESERVE address,bytes is an implemented compile-time declaration outside IF: both unsigned numeric literals must be multiples of 256, with a nonzero range wholly inside a free portion of one user-arena span. Declare up to eight regions before allocating the program, normally on its first numbered line. Allocation and collection exclude the full region, with bounds stored outside user RAM. RUN, CLR, edits and CLEAN preserve reservations; NEW releases them. SAVE/LOAD retain numbered declarations. Identical bounds are idempotent; occupied/overlapping bounds fail safely. Removing source or a failed import may leave a reservation until NEW. $C000 is not implicit scratch RAM, and stock BASIC memory-top POKEs at 55/56 do not configure this allocator.
Allocator and compact objects
Use a coalescing, address-ordered free list per span. An allocated block has a two-byte little-endian physical byte size, including the header. There is no per-object type, owner pointer or allocated-list link. The owning anchor, symbol or descriptor supplies the type and address. A freed span stores size and next-free pointer in four bytes; ensure all allocations occupy at least four physical bytes. Strings of length one therefore consume four bytes, not three.
Line payloads are exact-sized and unaligned: allocation header, token-length byte, tokens and code, with no padding after the final JMP. This makes the allocator’s end address the native-body end. Two-byte addresses and sizes remain necessary because the arena crosses 256-byte pages and can exceed 32767 bytes. Check physical-size addition with wider arithmetic; language word wrapping never applies to allocator sizes.
Allocate stable line anchors in packed slabs in the common span. A slab has a shared two-byte allocation header, a two-byte next-slab pointer, a one-byte used count and 35 seven-byte slots: 250 bytes when full. Search populated slots for line numbers instead of maintaining a second per-line index. Stable binding records also remain in common RAM; their names and other movable data can use shadow RAM.
Collection and stopped rebuilding
The implemented runtime collector is nonmoving mark-and-sweep with free-list coalescing. It never moves string payloads, line code or native return addresses. It enumerates physical allocation boundaries and retains objects reachable from source, slabs, names/bindings, arrays/functions, descriptors, expression temporaries and live helper roots. It marks roots once per 2 KiB address window in a 256-byte bitmap over inactive lexer/compiler scratch at $0E00-$0EFF. A monotonic sorted-free-list cursor avoids repeated searches while inserting reclaimed blocks; coalescing follows the sweep. Headers retain full 16-bit allocation sizes. All collection boundaries occur outside active lexing/compilation, and no additional user-arena allocation is needed. It runs wholly within copied RAM helpers. Fragmentation can prevent allocation despite sufficient total free bytes. Direct CLEAN now rebuilds source, anchors and bindings into a second graph, densely remaps names, clears values/continuations and collects the released graph. It requires temporary headroom; general sliding arena compaction remains pending.
For stopped payload compaction, invalidate CONT and active function definitions, and clear values under the documented rebuild operation. Copy the at-most-255-byte source stream to scratch, reserve a nonoverlapping destination, then regenerate that line’s code there using the same stable names, anchors and RAM-helper ABI. Commit its new payload/body fields only after validation and release the old allocation afterward. Preserve its successor trailer and validate its predecessor link. Internal absolute labels, literal pointers and function entries are emitted afresh. No relocation records are retained.
The sizing pass computes the exact destination size while the old payload remains valid. Version 1 does not destructively overlap a live source/code block to obtain compaction space. If staging or regeneration fails, retain the old line; earlier individually committed moves still form a valid program. This conservative policy can fail to compact an arena with no sufficiently large free span. NEW releases all slabs, name bindings and payloads. Total free bytes do not guarantee a successful allocation.
5 Line representation and executable linkage
Seven byte stable anchor
Every entered or forward-referenced line has a stable seven-byte anchor. All words are little-endian. The executable entry is the anchor address itself. The sorted live list is represented by the native trailer operands, so the anchor stores neither a next pointer nor a previous pointer. A global head word starts traversal; RUN_END is the end sentinel.
Offset	Bytes	Field
$00	1	$4C, the absolute JMP opcode
$01	2	Native body address for a live line; RAM UNDEFINED_LINE for a missing target
$03	2	Unsigned line number, 0..63999
$05	2	Payload pointer; zero means unresolved or deleted

A nonzero payload is sufficient to mark a live line. Unresolved and deleted anchors have identical runtime behavior, so they need no separate state bits. Compiler diagnostics reside in generated error calls, not a node field. Use one global program-generation word for CONT invalidation; there is no per-line generation, incoming-reference count or reserved field.
Single source and code allocation
Location	Bytes	Meaning
payload - 2	2	Physical allocation size, including these two header bytes

T and C in this table are byte counts, not stored fields named T and C. The body starts at payload+1+T, equal to the anchor’s JMP operand. The allocation end is payload-2+physical_size. Derive C by subtracting the body address from that end, and derive the trailer address as end-3. The fixed per-line bookkeeping is seven anchor bytes plus three payload bytes, with about 0.14 shared slab bytes per occupied slot when slabs are full. Source bytes and native code are additional.
Reading the trailer’s operand yields the linked-list next entry. LIST and editing use a bounded common-RAM accessor when the payload is under ROM. Verify $4C before following the operand, accept only a live anchor or RUN_END, and use cycle/range checks while validating program integrity. The compiler and LIST must not use an untrusted arbitrary jump operand as a pointer without validation.
Sequential execution takes JMP next_anchor followed by the anchor’s JMP body. This costs one additional three-cycle JMP per line boundary compared with direct body-to-body linkage, while preserving all branch targets when a line’s variable-size payload is replaced. Every physical numbered body ends with the trailer even if END, GOTO, RETURN or STOP makes it unreachable.
Insertion replacement and deletion
For lines 10, 30 and 50, traverse head10 through the trailer links. Inserting 20 sets line20’s trailer to anchor30 and changes line10’s trailer operand to anchor20. Replacing 30 keeps anchor30, gives its new body the saved old successor anchor50, and changes only anchor30’s body/payload fields. No independent logical next pointer can disagree with the executable successor.
Locate predecessors by traversal rather than paying two bytes per line for a reverse link. Deleting a live line patches its predecessor trailer to its successor, or changes the head if it was first. Set the removed anchor’s payload to zero and its entry to RAM UNDEFINED_LINE, then release its source/code allocation. The runtime reports a missing target in the originating line; an unexecuted missing branch is legal.
Keep unresolved and deleted anchor slots until NEW or an explicit complete rebuild. This removes reference counts, incoming-reference lists and reclamation work from normal edits. It can retain memory for many historical line numbers; report that slab occupancy separately. An optional stopped sweep may scan branch tokens and release unused slots, but it is not required for version 1 and must never reuse a still-referenced anchor.
Eliminating persistent auxiliary tables
GOSUB, FOR and STOP continuations hold native PCs. A running or suspended program’s code never moves; edits, LOAD, NEW and stopped rebuilding invalidate all saved continuations before structural changes. Continuation entries emit their own source-context setup. This removes statement ordinal/offset tables from every line and shortens software frames.
DATA cursors scan typed source tokens using an anchor and one-byte token offset; no per-line DATA index is stored. Line anchors and stable cells keep inter-line and variable targets fixed. Rebuilding code from retained tokens resolves internal labels, literals and function entries, so persistent relocation records are also unnecessary. The price is compile work during stopped compaction and linear searches during editing and DATA traversal.
6 Tokenization and canonical listing
Compact binary source
Appendix A defines custom format version 1. Punctuation and keyword codes occupy one byte. A reference to interned name IDs 0..127 also occupies one byte; larger name IDs use a three-byte extended reference. Most small programs therefore use one byte for every nonliteral token. An unbounded full-name namespace cannot be represented by a single global byte, so the explicit extended form avoids a 128-name language limit.
Tokenize valid decimal and hexadecimal numbers into binary words during entry. Decimal 0..15 has a one-byte compact code; 16..255 uses a code plus one value byte; 256..65535 uses a code plus two little-endian bytes. A hexadecimal immediate uses a distinct code plus two bytes, preserving its radix for LIST. No ordinary valid numeric occurrence retains decimal digit text. Leading signs remain operator tokens.
Intern each full uppercase name once and store its ID in the token stream. The name dictionary retains its full spelling, suffix and length. Array/scalar usage is determined by syntax and binding kind, so the same name ID can refer to distinct scalar and array records. Strings, comments, nonnumeric DATA fields and malformed/unsupported numeric spellings use bounded length-prefixed payload tokens. Their payload bytes can have any value without being mistaken for token codes.
Interactive entry accepts at most 80 PETSCII characters per logical screen-editor line. Stored token streams have a byte length from 1 through 255, independent of expanded character length. Import can therefore contain a long dictionary name that occupies one token byte. Runtime strings may reach 255 bytes, but a single source-literal payload must still fit inside its line’s 255-byte token budget. Reject input or token expansion beyond the applicable limit explicitly.
Tokenization removes outside-literal whitespace and abbreviations. It validates full identifier boundaries and numeric magnitudes before choosing the smallest encoding. Keep a bounded temporary parser representation or parse twice for sizing and emission; no full AST persists. Dictionary allocation is part of the edit transaction, and malformed input is stored only through defined raw/recovery forms, never as arbitrary bytes mixed into the instruction vocabulary.
DATA representation
Within DATA, numeric fields use the same binary immediate codes and optional unary sign. Quoted strings use string tokens; nonnumeric unquoted fields use DATA_TEXT. Commas and the unquoted colon are ordinary delimiter tokens. READ consumes typed fields directly for numeric destinations, avoiding repeated numeric parsing of canonical integer DATA.
A numeric DATA field may also be read into a string. Preserve its original trimmed field spelling only when it differs from the canonical expansion, using the optional DATA_SPELLING payload after the binary value. For example DATA 001 stores binary 1 plus the spelling 001, so READ A$ still obtains 001. Canonical DATA 53248 needs no spelling payload: its binary value is signed -12288 for READ A, while unsigned source expansion 53248 supplies READ A$. This exception stores formatting evidence, not a second numeric representation to evaluate.
Test trimming, quoted/unquoted fields, signs and empty fields against the chosen BASIC compatibility subset. A DATA_SPELLING record must preserve the binary field’s unsigned magnitude, radix and optional sign; compare the complete field, not its immediate before unary negation. Reject mismatches on file import. Unsupported floating numeric DATA is listable as NUMTEXT and traps when consumed as a number; reading its preserved text into a string remains possible.
Canonical LIST rules
LIST traverses the live trailer chain, prints decimal line numbers and expands tokens with canonical spacing. Calls and array/DEF FN argument lists attach the opening parenthesis to the name; opening/closing delimiters have no interior padding. Keep spaces around assignment/arithmetic/comparison/logical operators, so TAB ( 11 ) becomes TAB(11), CHR$ (147) becomes CHR$(147), and X=(1+2)*3 becomes X = (1 + 2) * 3. No gap precedes comma/semicolon; ordinary separators remain between arguments and statements. Expand keyword abbreviations and preserve complete identifier spelling. String, REM and DATA payload bytes are preserved; signed DATA values keep their sign attached. Decimal immediates retain unsigned source magnitude and hex prints $ plus four uppercase digits. PRINT/STR$ still use expression-directed runtime formatting. Both target/host tokenizers accept whitespace before TAB/SPC opening parentheses.
Thus an entered 0001 becomes 1 in ordinary source, $d becomes $000D, and decimal 53248 never becomes -12288 merely because its runtime word is negative. Preserve exact string/comment and DATA_TEXT bytes. In DATA, keep a unary sign adjacent to its number; when DATA_SPELLING exists, print it as the whole field instead of the default sign/value expansion. This preserves READ into strings without duplicating the displayed number. Invalid or unsupported spellings remain visible through their recovery tokens. No original whitespace or spelling copy is stored for normal tokens.
Entered:  10 ?scoretotal%+0001:goto 30
LIST:     10 PRINT SCORETOTAL% + 1 : GOTO 30

Entered:  20 a$="PRINT : DATA":rem keep  these bytes
LIST:     20 A$ = "PRINT : DATA" : REM keep  these bytes

Entered:  30 video=$d000:poke video+33,1
LIST:     30 VIDEO = $D000 : POKE VIDEO + 33, 1

Tokenizing a canonical listing with the same name dictionary must reproduce identical canonical tokens for valid source. With a rebuilt dictionary, compare token meaning and full names after ID remapping. Keep recovery forms distinguishable; they need not promise byte-identical spelling repair beyond their preserved raw spans. LIST works even when the corresponding native body contains a syntax or unsupported-feature stub.
7 Compile on entry and transactional editing
Treat a numbered edit as a transaction. Traverse to locate the stable anchor, predecessor and current successor; tokenize into scratch; intern names; reserve forward-target anchors; parse, bind and size; allocate an exact source/code payload; then emit the native body. A counting pass and emitting pass use the same parser and helper ABI. Verify the generated body starts immediately after tokens and ends with the successor JMP.
Parsing discovers static types and native templates without a whole-program pass. DIM and DEF FN bind stable records but allocate array payloads or activate definitions at runtime. Forward GOTO/GOSUB targets reserve empty anchor slots. Dynamic array and control-stack validity is checked while executing.
Retain malformed and unsupported source in defined tokens so it can be LISTed and repaired. Numbered submission reports lexical/assembly failure immediately, while saving tokens and a deferred runtime error stub; successful submission and deletion resume input without READY. An enclosing false IF still skips its malformed unchosen body. Resource failure retains the previous source/code payload.
Edit	Commit changes
Insert	Publish payload and anchor entry; patch predecessor trailer or head. New trailer already points to successor.
Replace	Publish existing anchor’s new payload/body fields. The new trailer retains the old successor.
Delete	Patch predecessor trailer or head, clear payload pointer, set entry undefined, release old payload.
Append	Patch former tail to new anchor. New trailer points to RAM RUN_END.

Commit only while execution is stopped. Set EDIT_BUSY, mask IRQs briefly, publish the pointer/operand changes from common RAM, restore IRQ state and clear EDIT_BUSY. NMI only records a pending request. Free superseded payloads after publication. Long compilation, hidden-RAM copies, I/O and collection occur outside the short critical interval. Staged name/binding allocations must roll back safely; unused reserved anchor slots may be retained as harmless tombstones.
Successful numbered edits clear values, array payloads, active function definitions and software execution stacks, invalidate CONT, and increment the global generation word. Stable binding cells remain because other code embeds their addresses. CLR clears values without destroying bindings or bodies; NEW destroys the whole program. Generation wrap is safe because edits explicitly discard saved continuations.
8 Native code generation and calling convention
Compiler structure
Use a hand-written, bounded precedence parser and statement parser in ROM. Maintain a compact intermediate operation sequence for one statement at a time, or generate twice from tokens. Emit direct loads, stores, arithmetic, tests and branches for common scalar operations. Call the fixed RAM helpers for multiplication, division, strings, formatting, devices, arrays and control-stack manipulation. Device helpers enter KERNAL through common RAM. Those calls implement semantic operations; they do not redispatch statement tokens.
Fold constants with exactly the runtime modulo-65536 arithmetic and signed interpretation rules. Consume the tokenizer’s validated binary decimal/hex values directly; file validation enforces the same magnitude and canonical-encoding rules. Arithmetic wrap generates an ordinary constant; division by zero, invalid literal ranges and illegal quantities generate a runtime trap at their evaluation point. Cache a loaded scalar within a side-effect-free expression, but not across KERNAL calls, SYS, USR, input or allocation. Do not remove PEEK, WAIT or function calls when that could change hardware reads or side effects.
Emit only documented NMOS 6502 instructions supported by the 6510. Keep decimal mode clear at every language boundary. For a conditional branch whose final destination cannot fit in -128 through +127 bytes, emit the inverse short branch over JMP absolute. A deterministic sizing pass can use long forms consistently, then optionally shorten local branches after offsets stabilize. Never truncate a displacement.
Runtime ABI
Interface	Convention
Integer value	A is low byte; X is high byte. Y is scratch unless a specific helper documents preservation.
Binary helper	Right operand in A/X; left operand in named two-byte zero-page scratch. Result in A/X.
String value	Pointer to a registered four-byte descriptor in a named zero-page pair; no unregistered payload pointer across allocation.
Clobbers	A, X, Y and arithmetic flags are caller-clobbered. Each helper declares zero-page scratch and maximum hardware-stack use.
Source context	CURRENT_LINE anchor and a one-byte token offset are set before a trapping or blocking statement and at resumable native entries.
Errors	RAM ERROR transfers through common RAM to the ROM reporter; restore prompt stack baseline/channels and report the source line.
Boundary invariant	Expression stack empty, D clear, port bits 101 for native code, registered string roots only; KERNAL calls use a gateway.

Generated bodies have a line-entry context prologue. Every native continuation entry sets source context and checks a pending break; ordinary internal paths can share the context already established. Emit a periodic poll on every potentially unbounded backedge and within long helpers, as well as at line entry. This prevents a one-line loop, WAIT or long string operation from ignoring STOP.
Example native body
; Source: 10 A% = A% + 1
; A_CELL is a stable two-byte symbol cell.
; Context setup and break polling precede this snippet.
        CLC
        LDA A_CELL
        ADC #$01
        STA A_CELL
        LDA A_CELL+1
        ADC #$00
        STA A_CELL+1
line10_trailer:
        JMP line20_entry    ; always final three body bytes

line20_entry:              ; first byte of the seven-byte anchor
        JMP line20_body

The increment above deliberately discards the final carry and ignores the signed overflow flag. It implements the same operation for a signed integer or an address word, including $7FFF->$8000 and $FFFF->$0000. Excluding context setup and the trailer, it occupies 17 bytes and takes 22 CPU cycles. The boundary trailer and entry add six cycles in two JMPs. These are instruction-level costs, not a measured overall speedup; screen output, device latency, IRQs and VIC bus stealing can dominate elapsed time.
9 Statements and control flow
Fall through and conditional branches
Every native body ends physically with its patchable successor JMP. IF ... THEN ... ELSE selects one colon-separated arm for the remainder of its physical line. ELSE binds to the nearest unmatched IF; either arm can be a literal line target. A false IF without ELSE reaches the trailer. Nested IF depth is bounded to 32 and per-line IF patches to 64; a bound failure retains source with a FORMULA TOO COMPLEX stub.
Literal GOTO targets compile to JMP anchor_entry. ON expression GOTO/GOSUB selects from a table of target anchors; selectors 0 through 255 are accepted, zero or above the target count falls through, and negative values or values above 255 raise ?ILLEGAL QUANTITY. Preserve source-order evaluation under the integer contract. Target literals are parsed as unsigned line numbers even above 32767. Dynamic GOTO expressions are not introduced as an extension.
GOSUB and RETURN
Do not implement BASIC GOSUB as a simple CPU JSR into a line body. Line tails JMP onward and RETURN must return to the statement following the call, including one on the same line. Before jumping to the callee, push a three-byte software frame: one tag byte and the two-byte native continuation PC. RETURN searches the tagged stack according to BASIC nesting rules, discards appropriate transient FOR frames, pops the frame and jumps to that PC. Its continuation prologue resets caller source context. RETURN without a frame reports the familiar error.
The hardware stack contains only bounded native helper calls and interrupt frames. The shared software control stack is separate, with explicit tagged frame sizes and overflow checks. Tags imply frame size, avoiding a separate size byte. Raw PCs are safe because RUN and suspended CONT never move code. Every edit or structural rebuild invalidates CONT and its PCs before changing a payload.
FOR and NEXT
A nine-byte FOR frame stores a tag, scalar cell address, word limit, signed word step and native continuation PC. Unsuffixed and % loop variables are supported; string/subscripted variables are rejected. Initialization/limit/step are evaluated once. NEXT compares using the loop variable interpretation, with signed STEP direction. Unsigned NEXT detects wrap or underflow so loops ending at 65535 or zero terminate. Existing signed boundary wrap and STEP-zero nontermination remain; polling stays active.
Use dynamic frames rather than requiring lexical FOR/NEXT matching at compile time. Preserve NEXT without a variable, NEXT with a variable, comma-separated NEXT variables, nested reuse of loop variables, and the stack-search/discard behavior of stock BASIC. Do not add a pretest that skips the first loop-body execution when the initial value is beyond the limit. Differential tests on integer-range examples define the precise stack behavior.
DATA and functions
DATA produces no executable work beyond normal line linkage. At READ, use a cursor containing an anchor and one-byte token offset. Scan typed fields and delimiters, read binary integers directly, and obtain text or spelling payloads for string destinations. Follow the shared trailer links to locate the next DATA statement. RESTORE resets the cursor to the first live line and scans forward. No DATA index or numeric text parse is required for a canonical integer field.
Support DEF FN with one numeric parameter and a numeric body. The definition statement activates a stable function record at runtime; a call before execution of its definition raises ?UNDEF’D FUNCTION. Generate the native function body inside its owning line allocation, with RTS as the expression-helper return. Insert a local jump around that function code on the numbered line’s ordinary fall-through path, and emit its entry address into the stable function record at definition execution. Preserve the parameter’s former value through a bounded software activation record. The containing numbered line still ends with its required JMP trailer. Clear active definitions on RUN/CLR while retaining compiled bindings.
10 Variables arrays and strings
Stable bindings and arrays
Intern each complete normalized spelling into a dictionary with a one-byte length, full name bytes and a 16-bit ID. The implementation compares complete spellings in a linked dictionary rather than using the proposed hash buckets. This has linear compile-time lookup cost but preserves every character and suffix. Scalar cells and separate array/function bindings remain stable; repeated source references carry IDs rather than repeated spellings. A, A% and A$ and SCORE and SCORETOTAL remain distinct.
Bind scalar references during compilation so native accesses name stable cells without runtime full-name lookup. Dictionary lookup and storage grow with complete spellings; repeated token references remain compact. Retain interned names and cells until NEW or a successful CLEAN rebuild that rebinds all source and code. Deletion cannot free a cell still referenced by native code. RUN clears values while retaining bindings.
Integer arrays contain two-byte elements; string arrays contain four-byte descriptors. Stable array records hold a movable payload pointer, dimension count, bounds and strides. DIM allocates at execution time, rejects redimensioning, and checks total element count and byte size before allocation. Each dimension’s upper bound is inclusive. Undimensioned arrays use the stock default upper bound of 10 when first accessed. Use a tested stock-compatible subscript order for strides; no code may assume a stock array-memory layout.
Indices must be nonnegative integers and within bounds. Check dimension products and offsets using wider temporary arithmetic before narrowing to 16-bit addresses. Generate fast constant subscript paths only when the array still undergoes runtime existence and bound checks. Payload movement updates the stable descriptor; generated accesses load the base pointer rather than embedding a potentially stale element address.
String ownership and collection
A string descriptor is four bytes: one-byte length, two-byte payload pointer, and ownership/root flags. Zero length uses a shared empty value. Version 1 copies literals and assignment results into heap-owned immutable payloads rather than storing lasting pointers into token source. Aliasing descriptors may share immutable payloads. Concatenation and substrings allocate new values; all assignments publish the new descriptor only after allocation succeeds. A byte length above 255 raises ?STRING TOO LONG.
Use the implemented nonmoving mark-and-sweep collector with registered descriptor and helper roots. Roots include scalar cells, array elements, expression temporaries and function state. Allocating helpers must publish temporary string pointers before a collection boundary. Pointer rewriting is unnecessary because payloads remain stationary; the tradeoff is fragmentation. Clear temporary roots at statement completion and error exit.
Implement LEN, LEFT$, RIGHT$, MID$, CHR$, ASC, STR$ and integer VAL. CHR$ accepts 0 through 255; ASC of an empty string is an error. Embedded NUL and other PETSCII bytes are valid runtime string data even though source/file encodings impose their own restrictions. PRINT outputs by descriptor length, not a zero terminator. Do not invent quote escaping for LIST; source literals follow Commodore quoting rules and CHR$(34) constructs a quote byte when needed.
11 Direct mode program execution and device services
READY and RUN lifecycle
READY runs the editor/compiler in the command map. Send the screen-editor carriage return returned by CHRIN to CHROUT before parsing every submitted command, numbered line, deletion or blank line. This advances the cursor before subsequent output or input. Successful numbered entry/deletion resumes input without another READY prompt. Recoverable lexical/assembly failure prints an error but saves the new line. Direct LIST starts on a new line and accepts LIST n, LIST low-high and open endpoints; bounds are inclusive unsigned line numbers 0..63999 and reversed bounds give an empty listing. Direct CLEAN rebuilds dense slabs/symbols, clears variables and invalidates CONT. Other direct statements compile into a transient native payload and synthetic anchor, execute through the RAM gateway and end at DIRECT_DONE. Direct BASIC opens the bank-3 split editor: 20 listing rows, one status row and four edit/output rows. F1 shows help; F3 opens an incremental line-number prompt, closed by Enter or any non-digit without submitting the pane. Off-screen F3/submission jumps retain up to three preceding BASIC lines, reducing context when wrapping would hide the destination. LIST polls RUN/STOP and pending breaks between lines. F7/QUIT close and clear, and RUN closes before execution. Bookmarks retain selected and top BASIC line numbers. Return copies the selection or submits a draft; ← (PETSCII 95) changes focus and discards the draft on return to the list. INS toggles insert/overwrite; CTRL+2 independently toggles literal control entry. Errors preserve drafts and return the cursor to the failed command start, adjusted for output scrolling, with diagnostics in the status bar. Cursor keys can revisit earlier visible pane lines; wrapped rows remain one logical line. Numbered submissions select the affected source line and bring it into view; the line-number highlight remains visible while editing. Keyboard INPUT, output and screen-clear controls stay within the pane, with no READY prompt. The visible draft is limited to 160 bytes; overlong source copying is rejected without truncation. KERNAL input/output vectors are restored on exit. Highlight only the line-number digits. Visible cursor moves use a cached row map without reformatting source. Scroll by shifting overlapping character rows and render only exposed rows, measuring wrapped line heights; leave listing color RAM in place. Skip unchanged-source refreshes and write only differing screen codes after source changes. Help saves/restores listing characters using inactive buffers. Row work at $0F80-$0FDF and the snapshot tail at $0FE0-$0FFF share the previously unused upper half of the 32-entry expression-stack page.
Pin a direct payload while any GOSUB frame can return to it. Command statements such as LIST, NEW, LOAD, SAVE and VERIFY transfer to the command subsystem through a gateway; any source/code inspection there uses hidden-RAM accessors. Direct code cannot call a ROM handler and continue executing from shadow RAM without a gateway return.
RUN clears values, continuation and software stacks, resets active function definitions and DATA state, validates anchors/trailers/source bounds and ensures the runtime image is ready. A low-RAM entry selects the execution map and jumps to the head anchor. RUN n requires that exact live line number, still clears values, and reports a missing statement if absent. Valid lines are not recompiled on every RUN. Native execution never dispatches source statement tokens.
STOP, END and RUN/STOP at safe statement boundaries save a native continuation PC and the global program generation, preserve values and freeze the software control stack below a saved top, then enter READY through common RAM. END omits the BREAK message. CONT after the final line reaches RAM RUN_END again. Direct commands may use frames above the frozen top; RETURN/NEXT cannot consume suspended frames. CONT validates the generation, reenters the execution map and jumps to the saved PC.
Blocking INPUT/device operations may abort without continuation unless their internal state is explicitly resumable. NMI aborts, direct STOP and runtime errors invalidate CONT in version 1. Defer asynchronous abort requests until the bank gateway and allocator are outside critical updates. This prevents abandoning a ROM service with the execution map or stack half restored.

INPUT, INPUT# and GET preserve the documented prompting, empty-field and channel behavior within the integer contract. The RAM decoder applies the same word-literal rules as the entry tokenizer. Numeric GET retains checked single-character conversion behavior. Verify PRINT commas, semicolons, carriage returns, positive padding, TAB, SPC and redirected CMD output against stock behavior.
KERNAL service boundary
Resident and banked helpers call SETNAM, SETLFS, OPEN, CLOSE, CHKIN, CHKOUT, CLRCHN, CHRIN, CHROUT, GETIN, READST, RDTIM and SETTIM through the common kernal_gate/bank_call ABI. Restore caller mapping/bank and documented results. Stage arguments originally under ROM into common buffers. Blocking input permits IRQs and resumes its nested bank frames. Nonreturning errors establish bank 0 through RAM error/READY recovery and reset the hardware stack. DEF FN activation consumes its original native return address in a RAM stub and reads the four inline operands through read_ram; hot FN calls remain in RAM.
Serial source files are streamed as bounded chunks through common RAM. Do not call unrestricted KERNAL LOAD into the arena: it could overwrite source/code, gateways or resident helpers. The ROM file wrapper enters bank-0 source transport through bank_call. KERNAL-owned state stays excluded from the arena. $0334-$03FF holds 152 bytes of service/output stubs and 52 bytes of editor state; $0A60-$0AFF holds the 160-byte editor draft. The keyboard-input stub shares the main gateway code span. Install contents after KERNAL initialization because RAMTAS clears page 3; preserve vectors through $0333 and keep tape transport unsupported.
PEEK POKE SYS and USR
All direct and stored user expressions execute in the RAM map. PEEK/POKE therefore see RAM at $8000-$BFFF and $E000-$FFFF, and real I/O at $D000-$DFFF. Both required V/POKE idioms reach the VIC background-color register $D021. Reading an old BASIC/KERNAL ROM address now reads RAM; this is an intentional map change. The command firmware may inspect ROM only through an explicit diagnostic access interface.
SYS uses a common-RAM trampoline and the stock $030C-$030F register convention to enter an unsigned address in the execution map. USR uses the configured vector at $0311-$0312 and the integer A/X ABI. User code beneath cartridge or KERNAL ROM is executable, but code that calls KERNAL at $FFxx must use the published common-RAM bank service rather than an unguarded JSR. Entering $FFD2 in the RAM map does not invoke KERNAL CHROUT.
Before resuming language execution, the trampoline restores the execution map and clears decimal mode. User code must return with the expected stack shape. POKE can still corrupt gateway bytes, allocation state, runtime helpers, hardware vectors or $0000/$0001; ordinary C64 memory access provides no protection. Supported reservations and the gateway ABI make deliberate machine-code integration possible without allocator collisions.
12 File formats and program persistence
Custom authoritative source container
SAVE writes Assembly BASIC source format version 1 for plain programs, as specified in Appendix A, or version 2 when binary reservations/blobs are present. Version 2 prefixes reservation descriptors before dictionary/source allocation and appends blob/type/palette metadata and exact bytes before the CRC. LOAD accepts both versions. The container has magic/version, names, sorted line/token records and CRC; it has no pointers, native bodies, anchors or C64 load address. SAVE, LOAD and VERIFY accept filename[,device[,secondary]], defaulting device to 8. The optional secondary is evaluated once and checked as a byte 0..255, then ignored for source-only .AB files. Use a Commodore sequential byte file; transport retains channel 2 regardless of the compatibility argument. Validate the complete argument list before emitting the file operation, so malformed file arguments cannot write/load first and raise a syntax trap afterward. Colon and ELSE are legitimate boundaries. LOAD keeps its existing staged publication and return-to-READY behavior. SAVE checks transport status during OPEN/output/CLOSE, then requires a complete DOS success response after closing the data file. Query secondary 15 using TALK/TKSA/ACPTR/UNTALK without allocating or closing another logical channel. Failed writes and DOS errors report DEVICE ERROR and release the temporary export map; source and binary data remain available for retry. Existing files are not overwritten automatically.
The native source format uses the compact vocabulary rather than stock BASIC V2 keyword assignments or linked PRG records. Existing stock tokenized PRGs require an external or optional text conversion path; they are not the native loader’s input. Canonical PETSCII text produced by LIST is the exchange representation for other editors and languages.
SAVE includes only names referenced by live source and assigns dense export IDs in ascending order of their existing IDs. Each export ID is therefore no greater than its original ID: remapping can shorten a reference but never widen it or overflow a valid 255-byte line. Rewrite references during serialization and omit unused tombstones, deleted names and values. LOAD stages a fresh dictionary in file-ID order with new stable bindings; it does not append names to the old program’s ID space. Pointer values never come from the file.
Validate magic, format version, limits, full name spelling, dictionary uniqueness, token payload lengths, minimal integer encodings, ID bounds, DATA spelling consistency, sorted unique line numbers, end marker and CRC before publication. Reject reserved codes and truncated payloads. A token count is a byte count, not an instruction count. Raw literal bytes can include zero and token-valued bytes, so zero does not terminate a record.
Transactional LOAD and bounded transport
Stream disk bytes through a bounded common-RAM buffer into a staged name/source graph, compiling each staged line with the standard sizing/emission path. LOAD replaces the old graph only after the entire container validates. If there is not enough space for both graphs, fail without erasing the old source; the user may explicitly NEW before loading. A valid source graph can contain generated error stubs, but never corrupt record structure or partly published code.
In-program LOAD leaves native execution through the command gateway and invalidates its control frames and CONT. Automatic chaining is outside version 1. Tape sequential-file support requires separate bounded transport and interrupt tests; unsupported tape forms must fail explicitly. Raw binary/machine-code loading is a separate utility with explicit destinations and reservations, not a disguised language-source LOAD.
VERIFY text exchange and native caches
VERIFY compares canonical serialized source, including dictionary remapping and CRC, against the file. It ignores allocator addresses and code layout. Text export expands the same tokens as LIST; a text importer invokes the whole-identifier lexer and immediately produces custom binary tokens. Text export cannot reproduce discarded outside-literal whitespace, decimal leading zeros or hexadecimal digit case.
Do not save machine code in version 1. A future native cache must include a cartridge/runtime ABI identifier and complete binding validation; discarded relocation tables cannot be assumed to exist. Invalid caches regenerate from retained tokens. The compact source container remains authoritative for LIST, editing and rebuilds.

The compact line cost is approximately 10.14 + T + C bytes with full anchor slabs: 7 anchor bytes, 3 source/allocation header bytes, shared slab overhead, token bytes T and code bytes C. No statement table or relocation list is added. If illustrative averages are T=18 and C=80, a line occupies about 108 bytes. Reserving 8 KiB of the 42 KiB raw arena for names, bindings, arrays, strings and edit headroom leaves roughly 322 such lines. This is a scenario calculation, not a promised capacity.
Compact IDs improve repeated full-name occurrences: a 20-byte name repeated ten times uses ten one-byte references plus one dictionary spelling, rather than 200 repeated characters. The dictionary and stable binding record still have costs. Large ID sets use three-byte references; comments and long strings do not compress. Binary constants can shrink five-digit numbers to three bytes, while decimal 0..15 needs one byte. Frequent historical edits can waste partially occupied anchor slabs and retain tombstones.
Measure compile latency, token/native bytes, actual metadata per line, fragmentation, hidden-RAM access cost and RUN startup copy cost. Measure runtime speed on integer assignments, branching, arrays, strings and device output with normal IRQ/VIC activity. Arithmetic and line chaining have no per-operation ROM mapping cost. KERNAL-backed I/O and IRQ service pay gateway transitions and interrupt-frame work. Report that cost separately from native execution speed.
Keep quantity, literal, allocation and bounds checks with the wrapping word arithmetic contract. Later optimizations may shorten local branches, fold constants and specialize array paths. The seven-byte anchor, final JMP/list link, safe context polls and helper ABI remain observable implementation invariants. A lower runtime base can increase helper space at the cost of user RAM; a larger/banked cartridge would change the hardware baseline and requires a separate design decision.
14 Implementation plan and acceptance tests

Appendix A Compact source token format
This appendix specifies Assembly BASIC source format version 1. Token values are unrelated to BASIC V2 ROM assignments. Hexadecimal byte values below use a $ prefix. All two-byte words are little-endian. A stored line is a byte-counted token stream, not a zero-terminated string. Its line number and name dictionary live outside that stream.
A1 Code space and decoding
Code range	Meaning	Encoded size
$00-$0F	Punctuation and arithmetic/relational operators	1 byte
$10-$19	Literal, raw-payload and extended-name forms	Code plus the payload defined below
$1A-$1B	Arithmetic shift operators << and >>	1 byte
$1C-$1F	Reserved; reject in format version 1	No valid encoding
$20-$6A	Statement, connective, function and special-variable codes	1 byte
$6B-$6F	Reserved; reject in format version 1	No valid encoding
$70-$7F	Decimal immediate magnitude 0..15; value = code - $70	1 byte
$80-$FF	Name ID 0..127; ID = code - $80	1 byte

Decode one code byte, then consume precisely its declared payload before interpreting another code. Payload bytes are never recursively tokenized. A length prefix is an unsigned byte; integers and name IDs in payloads are unsigned words. The line byte budget includes every prefix and payload byte. There is no EOL token, padding token or implicit zero terminator.
Code	Punctuation or operator	Code	Punctuation or operator
$00	:	$08	/
$01	,	$09	^
$02	;	$0A	=
$03	(	$0B	<
$04	)	$0C	>
$05	+	$0D	<=
$06	-	$0E	>=
$07	*	$0F	<>
$1A	<<	$1B	>>

The parser assigns unary/binary meaning to + and - by context. Compound comparisons have single canonical codes; accepted alternate source orderings normalize to these spellings. TAB( and SPC( below include their opening parenthesis, saving a byte; their closing parenthesis remains $04. Other function names use a separate $03 opening parenthesis.
A2 Payload forms
Code and name	Following payload	Rules
$10 DEC8	One unsigned value byte	Canonical only for values 16..255.
$11 DEC16	Low byte, high byte	Canonical only for values 256..65535.
$12 HEX16	Low byte, high byte	All words 0..65535; LIST emits exactly four hex digits.
$13 STRING	Length byte, then that many PETSCII bytes	Quoted source literal; quotes are not stored. Empty length is valid.
$14 REMTEXT	Length byte, then raw remainder bytes	Must immediately follow REM and consume the rest of the token stream.
$15 DATA_TEXT	Length byte, then unquoted field bytes	Only inside DATA; no quotes, commas, colons or line endings. Zero length is an empty field.
$16 DATA_SPELLING	Length byte, then original trimmed numeric-field bytes	Only after a numeric DATA field; nonzero length and matching magnitude/radix/sign.
$17 NUMTEXT	Length byte, then unsupported numeric spelling	Fractions, scientific notation or oversized numeric source retained for listing and a reached trap.
$18 BADTEXT	Length byte, then malformed source span	Nonzero length; a reached lexical/syntax error, never executable text.
$19 NAME16	Low byte, high byte of name ID	Canonical for IDs 128..65534. $FFFF is invalid.

Ordinary integers require no textual spelling payload. Decimal leading zeros disappear when tokenized. Hex digit case and width are discarded while radix is retained. Invalid numeric values do not wrap at entry: oversized decimal/hex forms use NUMTEXT or BADTEXT with the appropriate generated error. String payloads cannot contain a literal quote because source has no quote-escape syntax; construct a runtime quote with CHR$(34). NUL and token-valued bytes are permitted in the binary payload when the input route can supply them.
An end-of-line unterminated string accepted by the legacy-compatible lexer stores STRING and LIST supplies its closing quote. In DATA, STRING represents a quoted field and DATA_TEXT an unquoted one, preserving that distinction. Numeric field grammar is an optional $05/$06 sign followed by a compact decimal or HEX16 immediate, optionally followed by one DATA_SPELLING record. NUMTEXT may serve as a text-preserving unsupported numeric field. DATA_SPELLING is never used outside DATA.
REMTEXT may contain commas, colons, quotes, zero bytes and values matching instructions. STRING may contain commas and colons. The decoder treats every payload byte as data, but valid unquoted DATA_TEXT must exclude source delimiters so LIST can reproduce the field without changing its meaning. A colon outside a payload ends DATA. Raw forms remain subject to line and string-length limits.

A4 Name dictionary and bindings
A dictionary entry’s identity is its complete uppercase PETSCII spelling, including any final % or $. IDs are unsigned 0..65534; no ID $FFFF is assigned. Length is 1..255 bytes. A spelling begins with a letter and continues with letters/digits followed by at most one final type suffix. Reject duplicate normalized names and exact reserved keywords/special variables. ID allocation is stable until NEW or complete source rebinding.
IDs 0..127 have direct one-byte codes $80..$FF. All later names use $19 followed by a two-byte ID, avoiding an artificial limit on full identifiers. Retaining a global dictionary minimizes repeated-name storage without paying a separate local name list for every line. The lexer and LIST consult the dictionary; native scalar operations use already bound RAM addresses and perform no ID lookup.
A and A() share a spelling ID but bind distinct scalar/array storage. A, A% and A$ have distinct IDs. Function and parameter uses resolve to their appropriate records. SAVE densely remaps referenced names in ascending original-ID order, which cannot widen a token. LOAD creates a fresh dictionary in file-ID order before compilation. Reserved tokens and runtime addresses never serve as dictionary IDs.
A5 Worked token encodings
Dictionary ID 0: V
Source: V=$D000:POKE V+33,1
Bytes:  80 0A 12 00 D0 00 37 80 05 10 21 01 71
Count:  13 bytes, excluding line number and shared dictionary

Source: V=53248:POKE V+33,1
Bytes:  80 0A 11 00 D0 00 37 80 05 10 21 01 71
Count:  13 bytes; DEC16 replaces HEX16

Dictionary ID 128: SCORETOTAL%
Source: SCORETOTAL%=65535
Bytes:  19 80 00 0A 11 FF FF
Count:  7 bytes

Source: DATA 001,53248,$D000,"A:B"
Bytes:  23 71 16 03 30 30 31 01 11 00 D0 01
        12 00 D0 01 13 03 41 3A 42
Count:  21 bytes; 001 is binary 1 plus exceptional spelling

In the first example, $80 is name ID 0, $0A is =, $12,$00,$D0 is hexadecimal $D000, $00 is colon, $37 is POKE, and $10,$21 is decimal 33. The final $71 is decimal 1. The line header supplies the byte count, so the zero bytes inside the constant and colon cannot terminate it. The DATA example’s colon byte $3A is inside a three-byte string payload and does not end DATA.
A6 Source file container
Field in file order	Encoding	Constraint
Magic	8 bytes: 41 42 36 34 53 52 43 00	ASCII AB64SRC followed by zero.
Format version	One byte: $01	Reject unknown versions.
Flags	One byte: $00	All bits reserved in version 1.
Name count N	Unsigned word	0..65535 entries, assigning IDs 0..N-1; last possible ID is 65534.
Dictionary	N repetitions: length byte then uppercase name bytes	Length 1..255; unique valid names; no address or value payload.
Live line records	Line-number word, token-length byte, exactly T token bytes	Strictly increasing numbers 0..63999; T=1..255.
End marker	Line-number word $FFFF	No length byte or tokens follow this marker.
CRC	Two bytes, low byte first	CRC-16/CCITT-FALSE over all prior bytes, including the end marker.

CRC parameters are polynomial $1021, initial value $FFFF, no input/output reflection and final XOR $0000. There is no C64 PRG load-address prefix and no serialized next-line pointer. EOF must follow the CRC. An empty program has N=0, no line records, the $FFFF end marker and its CRC. A sequential file’s bytes are decoded by Assembly BASIC rather than loaded verbatim into the CPU arena.
The container deliberately separates name spelling from occurrences and excludes native code. Import validates the complete container before replacing the live graph. Export dictionary compaction may change token ID bytes without changing source meaning. A native-byte dump or stock BASIC PRG is not this format, even if a filename has a .AB extension.
A7 Canonical validation and invariants
Valid binary streams use the smallest decimal encoding, direct name codes for IDs below 128, and nonzero payload lengths for BADTEXT, NUMTEXT and DATA_SPELLING. Require REM followed by exactly one REMTEXT token. Check DATA-only forms in context, reject delimiter bytes in DATA_TEXT and require numeric fields to use binary values rather than hiding them in DATA_TEXT. Validate syntax separately from lexical structure: safe tokens may still compile to a reached BASIC syntax error. Reserved codes, out-of-range IDs or payload overruns cannot enter the live graph.
Keep source tokens authoritative. Constant folding modifies native code only. Canonical LIST and the text importer must preserve numeric magnitude/radix, full names, signs, literal bytes and DATA spelling semantics. A format version change is required before reassigning any code or altering its payload interpretation.

Recorded architectural decisions
Stable anchors/bindings allocate from the low end of free spans; payloads and runtime heap objects allocate from the high end, preserving common RAM for future anchor slabs. Common allocations are checked against the $8000 boundary even for whole free blocks.
Runtime ABI 7 reserves $E400–$FFF9 (7,162 bytes); $FFFA–$FFFF holds hardware vectors. The allocator spans [$2C00,$D000) and [$E000,$E400), totaling 43,008 raw bytes. The resident compiler reserves $1400–$2BFF (6,144 bytes). The runtime base keeps the design's permitted lower-base adjustment.
The fixed-address runtime and resident compiler occupy raw images in banks 2 and 1. Cold start copies both images through common RAM; RUN and CONT refresh the runtime image without moving user code. The link output proves its RAM addresses; no runtime relocation is assumed.
String collection is nonmoving mark-and-sweep, followed by free-list coalescing, rather than the proposed compacting collector. Roots include line/slab/name/binding objects, arrays, functions, direct code, descriptors, expression temporaries and live helper string pointers. It marks roots once per 2 KiB window using a 256-byte bitmap over inactive lexer scratch, and sweeps the sorted free list with monotonic cursors. It avoids descriptor pointer rewriting but can leave fragmented free space.
Name interning compares complete normalized spellings through a linked dictionary. It preserves full identity but has linear compilation lookup rather than hash buckets. Scalar references bind stable cells at compile time.
Language zero page is $02–$78; KERNAL service state uses $90–$FF. Common workspace is $0800–$13FF. A supported stock KERNAL audit remains a release requirement.
$0334–$03FF (204 bytes) is firmware-owned common RAM: 152 bytes hold service/output entry stubs and 52 bytes hold editor state. The main gateway holds 593 code bytes and a keyboard-input stub; $0A60–$0AFF holds the 160-byte editor draft. Cold start copies the stubs after KERNAL initialization because RAMTAS clears page 3. Tape transport remains unsupported. See the banked-service ABI.
Runtime ABI and source-container version are separate. Source-only files remain version 1, with version 2 for binary metadata, magic AB64SRC\0, little-endian fields and CRC-16/CCITT-FALSE. Host validation is authoritative for the complete Appendix A structural and canonical checks currently implemented.

Revision 0.10 integer arithmetic — 13 October 2026

Assignment copies the low 16 bits without range checking.

Revision 0.7 unsigned words and FRE — 12 October 2026

Revision 0.5 semantics
Enter explicitly outputs the screen-editor carriage return before parsing/output, including blank lines. Successful numbered edits/deletions produce no READY prompt. Recoverable lexical/assembly failures report an error and retain their tokens and deferred runtime trap. Resource exhaustion retains the previous line.
LIST accepts exact numbers and inclusive/open ranges in 0–63999; a reversed range produces an empty listing. It emits a newline before the first listed line.
ELSE binds to the nearest unmatched IF on its physical line; colon-separated arms and literal line targets are supported. An unchosen arm does not execute. The compiler bounds pending IF depth to 32 and patch count to 64.
RND uses a full-period word LCG, state = (25173*state + 13849) mod 65536. First positive use seeds from the low word of RDTIM, zero repeats, and a negative argument supplies its complete two's-complement seed before advancing. It returns every word bit; normal display is signed.
Shift counts are checked unsigned bytes. Arithmetic right shift sign-extends; left shift wraps. Counts ≥16 saturate to zero/sign fill. Precedence from high to low is power, unary +/- , multiplication/division, addition/subtraction, shifts, comparisons, NOT, AND, OR. Existing eager evaluation and left associativity remain.
Literal power-of-two multiplication in either operand uses the shift helper. Literal power-of-two divisors use a biased arithmetic shift that preserves signed division toward zero; the $8000 word divisor (-32768) additionally negates the quotient. General variable arithmetic retains the generic helpers.
CLEAN is direct-only. It serializes referenced source to a temporary RAM container, builds a second graph, densely rebinds names and slabs, publishes it, clears values/continuations and collects unreachable objects. Referenced missing targets retain undefined anchors. Snapshot/rebuild allocation failures restore old source and release temporary storage. CLEAN needs temporary headroom and does not promise sliding compaction of every arena object.
RESERVE (token $6A) is a compile-time declaration outside IF. Its unsigned literal address/count must be multiples of 256, with a nonempty range wholly inside one arena span. The allocator removes a wholly free range atomically, preserving free fragments of at least four bytes; up to eight ranges live in fixed common state, outside the writable user regions. Collection skips these regions without reading user bytes as headers. Duplicate bounds are harmless; occupied/overlapping regions fail safely. RUN, CLR, edits and CLEAN preserve reservations; NEW releases them. SAVE/LOAD retain numbered declarations. Removing source or failed import does not release reservations before NEW.
Void Runner previously used $C200–$C217 as star data while compiled BASIC lines 400/410 occupied the same bytes, causing execution of overwritten instructions and a CPU JAM. Its first line now reserves $3C00–$3DFF and $C000–$C2FF. The stock BASIC memory-top POKEs at decimal 55/56 have been replaced; this language has separate zero-page ownership.
Program reset/clear helpers reside in the compiler image. Revision 0.6 replaces the earlier compressed images with raw banked copies.
The later Void Runner freeze was a very long collection pause on a valid heap. Captured-heap replay now takes 1,269,981 simulated CPU cycles for a full collection versus 137,980,792 cycles for only the old collector's remaining work. Both produce the same nine free blocks and 5,651 free bytes, preserving all live allocations and reserved game regions. See the investigation and measurements.
Error output and command allocator wrappers share the resident compiler image. Its RAM reservation remains unchanged in revision 0.6.

Magic Desk cartridge architecture — revision 0.16
The cartridge is 64 KiB, divided into eight 8 KiB banks mapped at $8000–$9FFF. The CRT declares classic Magic Desk type 19, EXROM=0, GAME=1, with one CHIP packet per bank. The raw binary concatenates banks 0 through 7. The format follows the VICE cartridge specification; VICE 3.7.1 cartconv accepts it and reproduces the binary exactly. This is the classic C64 format, rather than Magic Desk 16K or Magic Desk 128.

Maps and bank ownership
Command execution uses $01 low bits 7: bank 0 at $8000, stock BASIC ROM at $A000, I/O and KERNAL visible. BASIC ROM is visible but the language does not call its routines. Generated native code uses low bits 5: cartridge/BASIC/KERNAL hidden, I/O visible. This retains writable shadow RAM and the existing program arena. Writes beneath visible ROM reach underlying RAM.
The bank latch at $DE00 is write-only. Firmware records its current bank at $0BE3 (CART_BANK), outside user allocation. Every firmware bank selection updates both locations. Do not infer the latch from a read of $DE00. I/O must be visible when writing the latch. Native user code that selects a different bank must update the shadow too if it expects interrupted banked operations to resume that bank; SYS/USR normalize the bank to zero on return.
Command dispatch, source formatting and transport run in bank 0, the split screen UI runs in bank 3, and cold execution services run in bank 2. The editor calls existing command/compiler routines through bank_call and hooks KERNAL input/output through common RAM. All instructions that select another bank and their return paths execute from the common-RAM gateway at $0800. copy_bank_image uses the shared bank_call ABI with IRQs masked for the copy, restores the original bank, complete $01 and flags, and consumes SOURCE/DEST/COUNT. Cold start copies the gateway and service entry stubs after KERNAL initialization, then bank 2's runtime to $E400–$FFF9 and bank 1's compiler to $1400–$2BFF. RUN and CONT refresh only the RAM runtime image; bank-2 services execute directly from ROM. There is no decompressor or instruction relocation.
KERNAL and IRQ gateways preserve the interrupted bank, temporarily select bank 0 for ROM service/recovery paths and restore it before returning. NMI handling stays in common RAM and preserves the selected bank. READY, source transport and SYS/USR returns establish bank 0 after exposing I/O. The first nine bytes of every bank contain the CBM80 signature and cold/warm vectors; auxiliary-bank vectors reach common-RAM recovery helpers installed at boot. Hardware reset starts in bank 0.
Firmware keeps the cartridge enabled and hides ROM through $01; it never writes $80 to disable the cartridge. Some Magic Desk hardware variants latch disable until hardware reset. User code must leave the cartridge enabled and preserve the gateway, runtime, compiler, vectors and language state.

Banked-service call ABI
Runtime ABI 7 adds bank_call, a common-RAM call gate. A call contains four inline descriptor bytes immediately after its JSR:
jsr bank_call
.byte BANK_SERVICES,7 ; bank 0..7, or $ff to retain the current bank; port low bits 5 or 7
.word rom_read_number ; little-endian target address
; execution resumes here
Arguments are A/X/Y and the service's documented common-RAM state. The gate reads the descriptor in the caller's original mapping, advances the return PC over the descriptor, and saves the complete $01, software bank shadow and caller flags on that call's hardware-stack frame. Setup and return mask IRQs; the callee receives the caller's interrupt mask with decimal mode clear. Each active call adds five stack bytes compared with an ordinary JSR, plus service/helper locals. Arguments and results do not depend on a shared saved frame.
The result is A/X/Y and the callee's N/Z/C/V flags. Return restores the original bank, complete $01 and caller interrupt mask, and clears decimal mode. The target and return addresses are stacked before IRQs are reenabled, so nested ROM calls, RAM callbacks and KERNAL calls can reuse dispatch scratch safely. The NMI handler records pending aborts without calling services or changing dispatch scratch. No ROM instruction switches banks or hides its own continuation.
The gate clobbers IO_A, IO_X, IO_Y, IO_STATUS, IO_MAP, GATE_FLAGS and its dispatch staging bytes; it does not borrow the language's indirect pointers. Each service documents or follows its existing helper-state clobbers. Descriptor bytes must be visible in the caller's mapping and use the valid bank/map values above. Descriptor and return-address arithmetic is binary even when a SYS caller arrives with decimal mode set.
kernal_gate, call_ram, file_entry and copy_bank_image use this ABI; image copying additionally keeps IRQs masked and restores the original flags. SYS/USR retain their dedicated register/return contracts and normalize bank 0 plus the execution mapping. The small read_ram accessor remains a direct common-RAM byte reader to avoid full dispatch overhead during source scans.
The migrated bank-2 services implement DATA traversal, READ conversions, RESTORE, DEF FN definition activation, file-operation staging, OPEN/CLOSE/channel selection, INPUT prompting/field acquisition and GET conversion. Shadow source, filenames and definition operands are read through read_ram; writes reach underlying RAM. Shared number/string/stack helpers are reached through RAM_CALL descriptors with bank $ff, map 5. Allocator/collector, expression/control state and hot DEF FN calls remain in RAM. The activation stub consumes the original native return address before dispatch, preserving the compiler's four inline definition operands; it resumes the native skip jump only after restoring the RAM mapping.
Nonreturning errors enter the existing RAM error/READY path, establish bank 0 and reset the hardware stack. LOAD retains its existing return-to-READY behavior. Normal blocking input leaves IRQs enabled and restores each bank frame after the KERNAL service returns.

Existing RAM reservations and the 43,008-byte arena retain their bounds; this change creates implementation headroom rather than adding user-arena bytes.
Bank 2 has 979 ROM bytes free with both images present. Filling all 1,240 bytes of runtime RAM headroom would require shifting some ROM services to another bank; the descriptor ABI already supports that placement change.
Future banked routines
The call ABI now supports moving additional cold helpers to ROM. Each migration must declare arguments, results, shadow reads, RAM callbacks, error behavior and stack use. Keep the allocator, collection, active control state and native return addresses in stable RAM. ROM helpers must enter common RAM before selecting a different bank.
Moving compiler work out of $1400–$2BFF could recover RAM, but requires auditing its calls into bank 0 and scratch ownership. Adding fixed-point values changes cell/array/expression layouts and arithmetic semantics; publish a new ABI and recompile all source then. Existing version-one .AB source files remain authoritative; stock PRG import is implemented and export is still planned. The editor uses bank 3; planned PRG export routines can share its spare space, planned numeric/PRINT and hardware extensions can use banks 6/7, while execution helpers are placed deliberately in RAM or reached through defined bank gates.
Runtime ABI is now 7 because helper entry addresses and the banked-service contract changed. Source-only containers remain 1; binary metadata uses 2. Both load. Hard-reset with the new cartridge and reload/reenter source; old snapshots contain the earlier ROM, gateways and compiled helper references.

Cartridge screen editor
Enter BASIC in direct mode to open the editor. The upper 20 rows show the program, row 20 shows the writing mode and shortcuts, and the bottom four rows hold the current draft and direct-command output. QUIT, F7, and RUN clear the screen and close the editor; RUN then executes the program. The selected BASIC line number and first displayed line number survive closing and reopening.
Key	Listing focus	Edit focus
Cursor up/left	Previous BASIC line	Move text cursor
Cursor down/right	Next BASIC line	Move text cursor within the pane

Wrapped source continues after the line-number column. Moving the selection past the listing frame advances or backs up the viewport by five BASIC lines, clamped at the program's ends. Only the selected line number is highlighted, even while editing; source text and continuation rows remain in normal video. Listing cursor moves update only number cells, and switching focus retains the highlight without detokenizing the listing.
Scrolling shifts the overlapping character rows in place and renders only the newly exposed rows. A clipped line at the bottom resumes in those new rows; wrapped lines determine the physical row count of each five-BASIC-line shift. Listing color RAM is initialized on entry and is never shifted or rewritten during navigation or source updates. When no rows overlap, the new viewport is rendered normally. Commands that leave source alone skip the listing refresh. Source changes compare displayed characters and write only cells that differ, including after identical edits. Numbered submissions move the selection to the affected line and bring it into view; deletion selects the next surviving line, or the preceding line when deleting the last one. Numeric bookmarks are resolved against the current program, including after NEW, LOAD, and CLEAN, so the editor never retains a pointer into freed source.
F3 opens a GO LINE prompt in the status bar. Each digit immediately selects the requested BASIC line, or the next higher line; requests beyond the program select its last line. Enter or any non-digit closes the prompt without submitting the edit pane. This includes F1/F7 while the prompt is open. The draft, text cursor, focus and writing settings survive, including during keyboard INPUT. Numbers are bounded to 0–63999; excess digits or overflow are ignored.
When a numbered submission or F3 jump selects an off-screen destination, the viewport includes up to three preceding BASIC lines. Wrapped context can occupy more than three screen rows; fewer predecessors are used if needed to keep the destination visible. Near the program start, all available predecessors are shown. An already visible destination does not scroll or redraw source text.
Numbered drafts add, replace, or delete program lines through the existing on-machine tokenizer/compiler. Successful numbered submissions clear the edit pane. A line number alone deletes that line. Failed submissions retain the draft, show the error in the status row, and position the text cursor at the start of the command that failed, accounting for any output scrolling. Recoverable compilation errors still retain malformed source in the program, matching ordinary direct entry. Correct the retained draft and submit it again.
Commands such as PRINT 123, LIST, SAVE, LOAD, and INPUT use the edit pane. LIST polls RUN/STOP and pending breaks between source lines. LOAD also imports stock BASIC PRG files. Output, wrapping, screen-clear controls, and scrolling stay within its four rows; there is no READY prompt there. Keyboard INPUT uses the bounded pane editor; file/device input and output continue through their original KERNAL vectors. Cursor keys can revisit earlier commands or output still visible in the pane. Wrapped rows remain one logical line; Return submits the logical line containing the cursor. Editing an earlier line retains the surrounding screen contents. Moving the cursor down from the last pane row does not scroll.
INSERT pushes subsequent characters right and uses the normal reverse cursor. OVERWRITE replaces the character at the cursor and displays it in reverse black. CTRL+2 toggles LITERAL independently of INSERT/OVERWRITE. The status bar shows both settings. LITERAL enters PETSCII control bytes as visible quoted-style glyphs and shows a cyan reverse L cursor. In LITERAL, cursor and HOME control codes become literal characters. Return, DEL, INS, CTRL+2, F1, F7, and the ← (PETSCII 95) focus key retain their editor functions. Other PETSCII control bytes are ignored while literal entry is off, including inside quotes. Literal entry follows the current insert/overwrite policy.
The visible draft can hold 160 PETSCII bytes, including its line number. A stored line whose canonical spelling exceeds that capacity remains listable and is rejected for copying with an explicit message, rather than being truncated and accidentally replacing the original source. Output above a draft is scrolled away as needed when typing wraps; moving the cursor alone never scrolls.
The UI lives in Magic Desk bank 3 and shares bank 0's canonical LIST formatter. The common-RAM CHROUT hook preserves registers, flags and user zero-page pointers. Hooks are restored on exit. Editor text occupies $0A60–$0AFF, and persistent state occupies $03CC–$03FF, outside the program arena and compiler, collector, and runtime scratch. $FB–$FE are borrowed as screen pointers while editing. The row map and scroll work occupy $0F80–$0FDF, the unused upper half of the existing 32-entry expression-stack page. Help saves the 800 listing characters in inactive TOKENS, LEX_BUFFER and BRIDGE buffers plus $0FE0–$0FFF; it restores those characters without reformatting the program or touching color RAM. The draft, INPUT command backup and frozen control stack remain intact.

Stock C64 BASIC PRG import
LOAD "PROGRAM",8 accepts both the native .AB source container and stock C64 BASIC V2 PRG files. Detection uses the bytes in the file, not its extension. Reads let Commodore DOS determine PRG/SEQ file type; SAVE continues to create native sequential .AB containers. Imported source is compiled on the cartridge. Empty programs replace the current program and clear the editor listing.
The importer accepts the standard little-endian load address $0801, followed by linked BASIC line records and the final zero link. It verifies physical next links, increasing line numbers in 0–63999, line terminators, supported stock token codes, file status and the final end marker. This follows the original BASIC line-link format and BASIC V2 token spellings. The load address identifies the format; bytes are streamed through the source converter rather than written over the cartridge's live workspace.
Stock keywords, operators and the two-token GO TO spelling are converted to native source before tokenization. Embedded strings and REM/DATA fields retain PETSCII bytes, including control glyphs and bytes that resemble keyword tokens. Stock variables retain only their first two significant letters/digits, including spaces ignored by stock BASIC: LONGNAME and LOONEY both become LO. Stock name significance therefore survives conversion into the native language's full-name namespace.
Stock signed integer names require a separate namespace because native % means unsigned. For example, stock A% becomes the signed native name PRGINTA, while stock A and A$ remain distinct. The prefix cannot collide with a stock name normalized to at most two letters/digits. Numeric execution otherwise uses the cartridge's existing wrapping 16-bit integer contract. This does not add floating-point execution: fractional/exponent source and unsupported expressions remain listable, editable source with the existing compiler/runtime diagnostics.
LOAD constructs a second source graph and publishes it only after validation. Malformed or truncated files, invalid links/numbers/tokens, allocation failure, or a converted line exceeding 255 text bytes roll back to the old program. Native token lines also retain their 255-byte limit. Appended machine code or resource bytes after the BASIC end marker are rejected rather than discarded; relocated or extended-dialect programs are outside this importer. Imported machine addresses and SYS/USR calls are not relocated.
After loading, use BASIC to inspect/edit the listing, RUN to execute supported source, and SAVE to retain it in .AB format. Stock PRG export remains planned.

Reservations and blobs

Numeric prompts accept decimal or $-prefixed hexadecimal. ← cancels a prompt; F7 exits. New blobs use the first available space in their reservation. A sprite always occupies 64 bytes. Types, bounds and colors change how bytes are interpreted; these operations do not initialize, relocate or copy the data. Resizing rejects bounds that exclude existing blobs. Blob bounds must fit their reservation and must not overlap another blob.
RESERVE declarations create entries marked (BASIC). Their bounds are read only in this editor; blobs can be created, moved and edited inside them. Manual reservations accept byte-granular bounds within the existing user arena. Their containing pages are excluded from source, code, heap allocation and collection; firmware, I/O and runtime memory cannot be reserved. Occupied allocator pages are rejected, preserving the current program.
There are eight logical reservation slots and sixteen blob slots. The existing allocator supports eight page ranges. Deleted or moved ranges remain protected until NEW, so removing metadata does not overwrite bytes with allocator headers. Their protected pages can be reused by other editor reservations. NEW clears all metadata and releases the page exclusions. SAVE/NEW/LOAD also consolidates page claims to the surviving logical reservations.

Files and program persistence
S/L prompt for a filename of up to 51 characters. .BIN is added when no extension is supplied. Disk operations use device 8 and a sequential byte stream. There is no load address, length prefix or metadata in a .BIN. Save writes the exact selected extent. Load stops at the end of the file or the selected extent; short files leave the remaining memory unchanged and long files never write past the boundary.
BASIC SAVE uses source-container version 2 when binary metadata is present; source-only files remain byte-identical version 1. Both versions can be loaded. Version 2 saves reservations, BASIC/manual ownership, blob bounds/types, each sprite's colors/mode, and the exact bytes in every blob. Unassigned reservation bytes are not included. All sections participate in the file CRC.
The v2 byte layout is the eight-byte AB64SRC/zero magic, version/flags 2,0, a one-byte reservation count and five-byte reservation descriptors (start word, size word, BASIC flag), followed by the unchanged v1 dictionary and line records. After the FFFF line marker comes a one-byte blob count. Each blob has an eight-byte descriptor (reservation index, start word, size word, type/multicolor flags, two packed palette bytes) and its raw data. The final two bytes are the CRC-16/CCITT-FALSE. Words are little-endian. Reservation descriptors precede compilation so even low-arena blob pages are protected before any source allocation.
LOAD stages source and metadata and validates the complete stream before writing blob bytes. It then reopens the validated file and restores data without needing an additional blob-sized RAM buffer; keep the file available and unchanged until LOAD finishes. CRC/truncation errors in validation preserve the old source, metadata and blob bytes. An I/O failure during the second pass can leave already restored bytes changed. As with existing staged source loads, NEW before loading can help when the old program occupies pages required by the incoming program. CLEAN and garbage collection preserve the metadata and protected bytes.
The host ab64.container codec retains metadata on its ProgramLines mapping, so dumps(*loads(data)) preserves the binary sections. Reservation and Blob objects allow creating v2 files on the host. Text decoding exports BASIC source only; use .AB or individual .BIN files to retain binary content.
Implementation and validation
Scenes are composed one row at a time and compared with screen and color RAM; only changed cells are written, without clearing the screen between updates. Visible hex navigation updates the old/new byte cells and the value footer. Sprite painting updates just its enlarged pixel and the preview data byte; cursor motion and palette selection leave the rest of the screen intact. Prompts also update only changed cells and restore their covered rows when dismissed.
ROM bank 4 contains the UI and bank 5 the metadata/reservation/file services. The existing bank-call gateway restores bank, mapping and interrupt state. Persistent metadata occupies $0200–$0258 and $02A7–$02FF, leaving KERNAL file tables and keyboard state intact. These ranges are firmware-owned. Transient buffers use existing inactive workspace, preserving the BASIC draft and frozen control stack. VIC registers and sprite pointers are restored on exit.

Proposed specification: 16-bit integer signedness and arithmetic
1. Numeric types
Variable syntax	Type	Range
A	Signed 16-bit integer	−32768 to 32767
A%	Unsigned 16-bit integer	0 to 65535
A#	16.16 fixed point	Separate arithmetic and conversion rules

Both integer types use a 16-bit word. Signed values use two’s-complement interpretation.
For a word w:
Unsigned value: w.
Signed value: w when w < 32768, otherwise w - 65536.
Changing integer signedness preserves the word. It does not perform range checking.
2. Evaluation and destination conversion are separate
Evaluate an expression according to its operands and operators. The destination must not influence earlier arithmetic.
After evaluation, the destination consumes or converts the result:
Consumer	Treatment of integer result
Signed integer variable	Preserve the word; interpret as signed
Unsigned integer variable	Preserve the word; interpret as unsigned
PRINT	Print according to the expression’s result type
POKE address argument	Consume the word as an unsigned address

Thus:
PRINT 20000 + 20000   : REM Prints 40000
A = 20000 + 20000     : REM A becomes -25536
A% = 20000 + 20000    : REM A% becomes 40000

PRINT -5 + 4          : REM Prints -1
A% = -5 + 4           : REM A% becomes 65535
The arithmetic result is identical regardless of destination. Only its final interpretation changes.
3. Integer literals
Constant-only arithmetic
In expressions containing only integer constants:
Nonnegative constants, including zero, are unsigned.
Negative constants are signed.
Operators follow the normal mixed arithmetic rules.
Result signedness follows operand types, not the mathematical sign of the answer.
Examples:
PRINT 4 - 5          : REM Unsigned 65535
PRINT -5 + 4         : REM Signed -1
PRINT 20000 + 20000  : REM Unsigned 40000
Contextual naked literals
When directly combined with a typed variable expression, a naked literal adopts that expression’s type if its value is representable in that type.
Literal value	Permitted interpretation
0 through 32767	Signed or unsigned, according to context
32768 through 65535	Unsigned
−32768 through −1	Signed

Examples:
N% + 2      : REM 2 adopts unsigned
N + 2       : REM 2 adopts signed
N + 40000   : REM 40000 remains unsigned; mixed arithmetic applies
N% + -2     : REM -2 remains signed; mixed arithmetic applies
The signed negative constant -32768 must be recognized before independently typing its magnitude 32768.
4. Context is local to each operation
Resolve literal context according to the expression tree, respecting precedence and associativity. Later operands must not retroactively change an earlier operation.
A% / 2 + B
Evaluate as:
2 adopts unsigned from A%.
Perform unsigned division.
Combine that unsigned result with signed B.
The addition has a signed result.
For:
A% + B + 2
evaluate as:
A% + B produces a signed result.
2 adopts signed from that result.
Perform signed addition.
An evaluated constant subexpression has its own type and is no longer an adaptable naked literal:
N% + (4 - 5)
Here, 4 - 5 independently produces unsigned 65535.
Parentheses around a literal alone need not prevent contextual typing: N% + (2) may behave like N% + 2.
5. Mixed integer arithmetic
Use the following type rule for binary integer arithmetic:
Left operand	Right operand	Operation and result type
Signed	Signed	Signed
Unsigned	Unsigned	Unsigned
Signed	Unsigned	Signed
Unsigned	Signed	Signed

For mixed operations, reinterpret the unsigned operand’s existing word as signed before performing sign-sensitive arithmetic. No wider intermediate or range check is implied.
Consequences:
A% = 40000
B = 2

PRINT A% / 2    : REM Unsigned division: 20000
PRINT A% / B    : REM Signed division: -12768

B = -2
PRINT A% / B    : REM Signed division: 12768
The last expression does not produce mathematical -20000: signed interpretation changes unsigned 40000 into signed -25536.
6. Arithmetic width and overflow
Integer addition, subtraction, and multiplication retain the low 16 bits of the result. Overflow wraps for both signed and unsigned arithmetic.
The result’s type determines how those bits are subsequently interpreted.
Implementation may share routines for:
Signed and unsigned addition.
Signed and unsigned subtraction.
Multiplication that returns only the low 16 bits.
Signedness remains significant for division, remainder, ordering comparisons, printing, and conversion to fixed point.
Division must select its signed or unsigned implementation after operand types have been resolved.
7. Constant folding
Constant folding, if and where implemented, must reproduce the specified typed, 16-bit evaluation at every operation.
A folder may use wider host arithmetic internally, but it must:
Apply the language’s operand interpretations.
Perform the operation.
Retain the specified 16-bit result.
Preserve the operation’s result type.
It must not infer signedness from the final mathematical value or postpone all wrapping until the end.
For example:
PRINT (4 - 5) / 2
must evaluate as unsigned 65535 / 2, producing 32767. Folding it through mathematical -1 / 2 would change its behavior.
8. Implementation record — revision 0.10
The signed/unsigned integer rules above are implemented by the 64 KiB Magic Desk cartridge, runtime ABI 6, retaining source format version 1. Numeric cells and array elements remain two bytes; expression tags remain signed 0, string 1 and unsigned $80.
Representable naked literals beside signed operands can retain their default unsigned tag internally: the mixed signed rule gives exactly the same operand interpretation and result type as adopting signed. This requires no extra runtime provenance and does not allow context to change an already evaluated operation. Positive constants never inherit the assignment destination's type.
Negative literal prefixes, including -32768 and -(2), produce signed words. Unary minus on computed expressions and declared values preserves their type: -(2+2) is unsigned 65532, whereas -4 is signed -4. Power retains its existing precedence; -2^2 is signed -4, while -(2^2) negates the already evaluated unsigned subexpression and produces unsigned 65532. NOT preserves numeric type; comparisons produce signed -1 or 0. Numeric functions keep their established declared result types (for example, VAL and RND are signed; FRE is unsigned; INT and ABS preserve the argument type).
Literal power-of-two multiplication uses wrapping left shifts. Signed division uses biased arithmetic right shifts to preserve truncation toward zero; unsigned division uses zero-fill shifts. Literal $8000 is unsigned 32768, interpreted as signed -32768 only in mixed signed division. General constant folding is not implemented; the same per-operation rules constrain the existing strength reductions.
The table's A# 16.16 fixed-point type remains a future extension; its conversion rules are outside this integer implementation. The design mentions remainder but defines no remainder operator syntax, so this revision adds none. Explicit >> retains the language's arithmetic sign-fill behavior for both integer types.
